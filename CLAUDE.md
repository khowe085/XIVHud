# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

**XIVHud** — a **Windower 4 addon** for Final Fantasy XI, written in **Lua 5.1**: a configurable HUD framework of composable widgets designed to work in the style of Final Fantasy XIV's HUD system, arranged through the addon's settings rather than one fixed display. Windower is a Windows-only launcher/injection platform that loads addons at runtime and exposes them a global API. The addon's source lives in **`src/`**; a GitHub Action packages it into a zip that users unzip straight into their Windower `addons/` directory (see Packaging & releases below).

Because addons run inside Windower on Windows, they cannot be executed or fully tested in this Linux devcontainer. Development here is authoring, linting, and formatting; runtime verification happens in a live Windower/FFXI client on Windows.

## Toolchain & commands

The devcontainer (Alpine) provides Lua 5.1, luacheck, StyLua, busted, and the GitHub CLI.

- **Test:** `busted` — runs every `*_spec.lua` under `tests/`, including `tests/components/` (config in `.busted`). Filter with `busted tests/core_spec.lua` or `busted --filter "layout"`.
- **Lint:** `luacheck .` — config in `.luacheckrc` (std `lua51`). luacheck auto-applies its `busted` std to `*_spec.lua`, so `describe`/`it`/`assert` need no whitelist.
- **Format:** `stylua .` (or `stylua --check .`) — config in `stylua.toml` (2-space indent). Also runs on save in VS Code via the StyLua extension.
- **Run a script standalone:** `lua <file>` — only for pure Lua with no Windower globals; anything touching the addon API must run inside Windower.

There is no build step. "Passing" locally means green `busted` + clean `luacheck` + `stylua --check`.

**Green locally does not mean it loads.** Nothing here exercises `require` resolution inside Windower, the real `texts`/`images`/`files` libraries, or the prim layer — and this addon has already shipped a build that passed every check and then failed to register a single event in the client. Treat any claim about the Windower API as unverified until it is read in the [library sources](https://github.com/Windower/Lua/tree/dev/addons/libs) or confirmed in a live client; the wiki documents what a function returns far more often than how it behaves at the edges.

## Windower addon conventions

These are platform facts about how Windower loads and runs addons:

- **Globals in `.luacheckrc`.** The whitelisted globals are `windower`, `texts`, `images`, `res`, `packets`, `_addon`. (`files` is deliberately absent — see the file I/O note below.) Two kinds are mixed here:
  - *Truly injected by Windower:* `windower` (core API — events, chat, packet send, ffxi/player/target data) and `_addon` (addon metadata: name, version, author, commands).
  - *Libraries assigned to globals by convention:* `texts`/`images`/`res`/`packets` are loaded with `require('texts')` / `require('images')` / `require('resources')` / `require('packets')` and conventionally stored in a same-named global; `files` similarly wraps addon-relative file I/O. See the Libraries wiki below. When you introduce a new global, register it in `.luacheckrc` so luacheck stays clean.
- **Addon layout.** Installed, an addon is a folder under `Windower4/addons/` whose main `.lua` **must share the folder's name** (Windower loads `addons/<folder>/<folder>.lua`). Here the source lives in `src/` and the packaging step wraps it in a folder named after the repository — so the main file is **`src/XIVHud.lua`** (the Action warns if it's missing). The main file declares metadata on the injected `_addon` table: `_addon.name`, `_addon.author`, `_addon.version`, and its commands. **The convention is `_addon.commands`, listing the primary name first** — of roughly forty addons in the Windower repository, all but one set either `_addon.command` (a single name) or `_addon.commands` (a list), never both. This addon currently sets both, which is redundant: it was added while chasing an addon that answered no commands at all, and the cause of that turned out to be elsewhere entirely, so which field Windower honours was never actually established. Reducing it to `_addon.commands` alone needs a live client to confirm `//hud` still routes. At runtime, user settings live under `<addon>/data/` — generated by the addon, never committed (gitignored, and stripped from the package); see Settings below for the per-component scheme this repo uses instead of a single `settings.xml`. Every source file carries the **BSD 3-clause license header** (Windower convention — © 2026, Azureblood2).
- **Settings.** This repo does **not** use Windower's `config` library — see Settings below. (For reference, the platform convention is `settings = config.load(T{...})` then `settings:save()`; `config` can only serialize XML, and the character name is not known until login, neither of which fits the per-component scheme here.)
- **Events.** Behavior is driven by handlers registered with `windower.register_event(...)`. Common events: `'load'`, `'unload'`, `'addon command'` (from the addon's command), `'incoming text'` / `'outgoing text'`, `'incoming chunk'` / `'outgoing chunk'` (packets), `'prerender'` / `'postrender'`, `'login'` / `'logout'`, `'zone change'`, `'status change'`. Text/chunk events may return modified data or a block flag.
- **Common libraries** (`require(...)`): `config` (Windower-XML settings load/save), `logger`, `tables`/`strings`/`sets`/`lists`/`functions` (data-structure & functional helpers), `resources`, `packets`, `texts`, `images`, `json`, `chat`. See the Libraries reference below.
- **Gotchas that cause real bugs** (fuller treatment in the mirrored Lua guide below):
  - `windower.ffxi.get_player()` / `get_mob_by_index()` can return `nil` (not logged in, index not loaded) — guard before indexing. A PC has both a permanent ID and a per-zone **mob index**; use `target_index`/index for in-zone lookups.
  - Windower and Lua **fail silently**: too few/many function args yield `nil`/dropped values, and undefined table keys return `nil`, all without erroring. A `nil` in an array also halts `ipairs`/`#` iteration early. Validate inputs yourself.
  - Tables are **1-indexed**; there's no built-in string split or table slice (use `strings`/`tables`). `T{}` (from `tables`) is needed for method-style calls like `t:map(...)`; convert the mob/player arrays with `T(...)`.
- **Library setters that are also getters** (verified against the `dev` sources; each cost real debugging):
  - `texts`/`images` accessors return the current value when called with **no argument**. `text:right_justified()` does not right-justify — it *reads* the flag. Always pass the value: `text:right_justified(true)`.
  - `stroke_transparency` and `transparency` take **0..1**, and internally compute `alpha = 255 * (1 - value)`. Passing a 0–255 alpha to them produces a wildly negative alpha. Use `stroke_alpha`/`alpha` for 0–255.
  - The guards are `if not x` / `x == nil`, and **`0` is truthy in Lua**, so a numeric zero is *not* mistaken for "no argument". `color(0, g, b)` and `stroke_width(0)` behave.
  - `image:fit(true)` sizes a prim to its texture, which defeats explicit `size()`. Anything scaled or stretched must set `fit(false)`.
- **Do not write config through the `files` library.** Reading its source suggests `files.new(path):write(contents)` creates any missing directories (`write` → `create()` → `create_path()` → `windower.create_dir`), and that reading is what this repo originally relied on — but `files.create` **ignores the error from `create_path`** and then indexes the nil handle from `io.open`. In practice that printed `New file: data/…` and produced no file, for days. `src/XIVHud.lua` builds each directory itself with `windower.create_dir`, checks the result, re-checks with `dir_exists` (success can be reported for a directory that is not there), and writes with plain `io.open`. Raw `io` against `windower.addon_path` is the one file operation proven to work here.
- **Other I/O facts** (verified): `windower.get_dir(path)` returns files and directories together, so classify entries with `windower.dir_exists`. A texture path that does not exist fails **silently** — the prim simply draws nothing.
- **Never shell out.** The addon runs inside the game process, so `os.execute` and `io.popen` flash a console window over the client. Every file operation here calls straight into the C library instead: `io.open` for reading and writing, `os.remove` for deletion — none of which create a process. `tests/sources_spec.lua` fails the build on a process-spawning call in `src/`.
- **Chat is not UTF-8.** Anything passed to `windower.add_to_chat` must be plain ASCII: an em dash reaches the player as `â€”`. Write `-` in user-facing strings, never `—`. Comments are exempt — they are never displayed, and the licence headers keep their `©`. `tests/sources_spec.lua` fails the build on a non-ASCII byte outside a comment.
- **`src/XIVHud.lua` traces its own load** to `<addon>/load.log` with raw `io` — every load step, `addon_path`, and the result of each `create_dir`. An empty file named `safe_mode` beside it loads the framework and commands but no component or render loop, which is the bisect to reach for when the client misbehaves. Both are load-time only and deliberately kept: an addon whose chunk dies is silent, and a client that then crashes takes the console with it. **Nothing traces from the render loop** — a heartbeat there found a crash once and was removed the same day, because per-frame disk I/O is not something to ship.

## Modular design & testing

Addons are structured so the logic is unit-testable **without a running Windower client**, using **dependency injection**. The rule: pure logic never touches Windower globals directly — it receives what it needs as a `deps` table.

```
src/
  XIVHud.lua              -- entry point: the ONLY file that reads Windower globals
  lib/                    -- the framework; pure, factory style `new(deps) -> instance`
    core.lua              -- orchestration: registry + settings + visibility + layout mode + commands
    registry.lua          -- component registration, enumeration, teardown
    settings.lua          -- per-component config service (data/<Character>/<component>.lua)
    serialize.lua         -- Lua-literal serializer with stable key order
    commands.lua          -- `//hud` parser -> action tables
    layout.lua            -- snap/clamp maths and per-slot layout state
    layout_mode.lua       -- `//hud layout` drag/scale/toggle state machine
    overlay.lua           -- layout-mode highlight box + name label per component
    visibility.lua        -- auto-hide suppression resolver
    icons.lua             -- pure item-icon extraction (DAT record -> bitmap)
    icon_cache.lua        -- the queue/cache discipline around it, shared by components
  assets/overlay.png      -- framework art (white square, tinted for the highlight)
  components/<name>/      -- ALL of a component's code, isolated per component
tests/
  *_spec.lua              -- one spec per lib module
  components/*_spec.lua   -- component specs, mirroring src/components/
  support/fakes.lua       -- fake deps, file system, prim recorder, widget
```

- **Pure modules (`src/lib/`).** Each returns a constructor `new(deps)`. It calls `deps.get_player()` etc. — never `windower.*` directly. Because deps are plain functions, a test "mock" is just a table of stubs; no mocking framework required.
- **Entry point (`src/XIVHud.lua`).** The only place that reads globals. It builds the real `deps` from the live API, wraps Windower's method-style prims (`t:pos(x, y)`) as plain function tables for components, constructs and registers each component, and wires `windower.register_event(...)`. Packets are pushed the same way: every `incoming chunk` is dispatched to every component as `update('chunk', id, original, parsed)`, and a component decides for itself, from the id alone, whether it is worth reading -- giltracker's own `logic.wants_chunk` does exactly that for item packets. `parsed` is non-nil only for the ids with more than one reader, which the entry point decodes **once** rather than once per consumer: the three party-list ids Windower has a field definition for (`packets.parse`, rather than once per sibling list), and the `0x028` action packet (`windower.packets.parse_action` — core API, not the `packets` library), wanted by targetbar's cast bar and the crossbar's skillchain engine, which parsed it one apiece until CB6. Both parses are `pcall`'d, so `parsed` is also nil when the decode failed, and the raw bytes always ride alongside it — a component that wants its own decode still has them. A fourth id the party list reads, and everything giltracker cares about, has no such definition and is decoded from the raw bytes by the component itself. `core.dispatch` walks every registered component regardless, so a component that does not want packets has to ignore the event rather than be spared it. Item movement is pushed too, narrower: `add item`/`remove item` dispatch as `update('add item'|'remove item', id)`. `gain focus`/`lose focus`, `gain buff`/`lose buff`, `job change` and `ipc message` are forwarded whole under their own names for the crossbar (input reset on alt-tab, context layers, the per-job binding reload, `warp all`). Keep it thin — anything worth testing belongs in `lib/` or a component.
- **Component isolation.** A component's whole implementation lives in `src/components/<name>/`, entry file `<name>.lua`. One directory may back **several registered names** where they are the same widget over different data - `partylist` registers `partylist`, `alliancelist1` and `alliancelist2` from one factory, told apart by `ctx.variant`. Three directories would force a cross-component `require`, which the rule below forbids outright, so one directory is the smaller deviation. It may require `lib/`, never a sibling component; cross-component needs go through the framework. The name is the shared key across code dir, config namespace, registry entry and command word, and is validated at registration (it cannot collide with a reserved `//hud` verb).
- **Widget contract.** `new(ctx) -> widget` exposing `name`, `defaults`, `attach(config, save, store)`, `detach()`, `set_pos(x, y, anchor)`, `set_scale(s, anchor)`, `set_preview(on)`, `show()`, `hide()`, `get_bounds(anchor) -> x, y, w, h`, `update(event, ...)` (no arguments is the per-frame tick), optional `handle_command(args) -> message` (a string, or a **list of strings** when one line will not do - an ordering or a search result; core says each), and `destroy()`. Four further members are opt-in, covered in the two bullets below: the `wants_store` flag, `anchors()`, `on_keyboard` and `on_mouse`. **A widget declaring none of them sees exactly the contract it always had** — `store` is nil, the trailing `anchor` argument is nil, and no input reaches it — which is why parambar, giltracker and the partylist trio needed no edits when the crossbar landed. Core owns visibility and layout persistence; a component never decides whether it is on screen. **`get_bounds()` must return the same origin `set_pos` was given** — core clamps the widget on screen by comparing the two, and layout mode's drag offsets assume it; on a multi-anchor widget that holds per anchor.
- **Multi-anchor widgets.** A widget whose pieces are placed independently declares `anchors() -> {names}` and moves `pos`/`scale` under those names in its default slot state (`slots.default.anchors.<name> = { pos = , scale = }`, no top-level `pos`); `visible` stays **per widget**, so layout mode's right-click toggles the whole thing and per-anchor visibility does not exist. Core then pushes, clamps, describes (`//hud list` prints a headline plus one line per anchor) and highlights one placement per anchor, and layout mode hit-tests per anchor — a drag or a wheel-scale addresses the anchor under the cursor, later anchors winning over earlier ones. Detection is **the member, never a convention**: absent `anchors()` (or when it answers a non-table), everything above takes the single-anchor path with the old signatures untouched — Lua's silent nil-tolerance makes an implicit rule too dangerous here. `layout.slot` keys off the *defaults* instead, and sheds a stray top-level `pos`/`scale` from an anchored entry as it repairs it. `crossbar` is the only multi-anchor component (`main`, `wxhb_left`, `wxhb_right`, `indicator`).
- **Component input.** `on_keyboard(key, down, flags, blocked)` and `on_mouse(mouse_type, x, y, delta)` are optional members; returning `true` propagates out to Windower as the block, and core ORs the answers together. The mouse signature carries no `blocked`: core answers an event a prior addon already took itself, so the flag would be false on every call a component could ever see - unlike the keyboard, which is forwarded whole precisely because core does *not* short-circuit there. Both handlers are registered for as long as *some* component declares one (`core.wants_keyboard()` / `wants_mouse()`), not just while layout mode is on, and `unload` releases them. **Layout mode owns the mouse outright** — while it is on no component sees a mouse event, and entering it exits a component's edit mode, so the two can never contend. Keyboard is the opposite by design (pinned 2026-08-16): core keeps **delivering** keyboard events during layout mode, under suppression and while logged out, so that a component *can* keep blocking its dedicated keys and tracking their state; the inertness belongs inside the component, not in dispatch going quiet — which would make blocking impossible. Delivery is all core promises: what a component does with an event is its own call, and a detached one (logged out, so nothing is attached) blocks nothing at all - the crossbar's keys go back to the game until a character is scoped. For that, core exposes `core.suppressed()` (the auto-hide resolver is hiding the HUD) and `core.component_visible(name)` (the user's own `visible` flag, what `//hud show|hide` and the right-click write, untouched by suppression). Both reach a widget as `hide()`, and only core can tell them apart: the crossbar ranks **disabled above suppressed** — suppressed means inert but still swallowing its five dedicated keys (handing `;` back to the chat box mid-cutscene would be worse), disabled means every key falls through to the game.
- **Tests (`tests/`).** busted specs `require` a module and pass fake deps. See `tests/core_spec.lua` and `tests/support/fakes.lua`. `tests/sources_spec.lua` is the exception: it `loadfile`s every file under `src/` so every file is at least known to compile, and checks the licence headers and the require convention. The entry point has a second exception of its own: `tests/entry_point_spec.lua` runs it, over `tests/support/entry_point.lua`, which `loadfile`s `src/XIVHud.lua` and hands it a fake `windower`, `io` and `require` through Lua 5.1's `setfenv` (`lib/core` and every component factory stubbed, `lib/guard` real). That covers the **wiring only** — what it registers, what each ctx is built from, and what the chunk dispatch pre-parses — because a decision made there is invisible to every component spec. It is not a licence to move logic into the entry point, and the harness header lists where each fake diverges from the client.
- **Require paths — use slashes, not dots.** Internal modules are required as `require('lib/core')` and `require('components/parambar/logic')`. Dot form *should* work (Lua's own loader rewrites `.` to the path separator), but the only addon in the Windower repository that requires across subdirectories — `bluguide` — uses slashes, and that is the form with evidence behind it. Both resolve under busted, because `.busted` sets `lpath` to include `src/` and `?` is substituted literally; at Windower runtime the addon's own folder is the require root, with `src/` as its stand-in here. `tests/sources_spec.lua` fails the build if dot form reappears.
- **A failed load must stay diagnosable.** If the main chunk dies part way, every `register_event` after the failure never runs: the addon answers no commands, writes no config, and cannot be investigated from inside the game — the worst possible failure, and one this repo has already hit. So `src/XIVHud.lua` loads in isolated steps that record why they failed, and registers the `addon command` handler **before** any of them; `//hud` then reports the failure. If loading fails, nothing else is registered and nothing is drawn.
- **Every Windower handler is wrapped** by `lib/guard`. `prerender` runs each frame, so an error there recurs sixty times a second and buries the one useful message; guard reports the first distinct error per handler, swallows repeats, and disables a handler after five failures. The mouse and keyboard handlers fall back to `false`, because a dead handler that keeps swallowing input is indistinguishable from a frozen client.

## Settings

Per-component isolation: every component owns its own configuration file and can never reach another's.

- **Storage:** `data/<Character>/<component>.lua`, relative to the addon root. Framework options live in `data/<Character>/core.lua` (`snap`, `slot`, `hideCutscene`). A component needing more than one file owns the directory `data/<Character>/<component>/` — the **store**: a component setting `wants_store = true` is handed `store` as `attach`'s third argument, `load(name)` / `save(name, table)` over `data/<Character>/<component>/<name>.lua`, same sandboxed read and serialized write as the component file. A name must be a plain word (`^[%w_]+$`) — it becomes a path segment, so anything else is refused rather than composed. Found files are cached until the config is re-read; a *missing* one is re-read from disk on every call, so callers load on their own events (an attach, a job change) and never per frame. `//hud reset <component>` empties that directory too (non-recursively — the store is flat by construction), and every re-read drops the cache, so `//hud copy`'s reload cannot leave copied bindings stale in memory. Only `crossbar` uses it (per-job bindings, `<MAIN>.lua` plus `SHARED.lua`).
- **Format: Lua, not XML.** Windower's `config` lib can only serialize XML and the bundled `json` lib has no encoder, so `lib/settings` owns persistence itself: files are read with `loadstring` in an **empty environment** behind a `pcall` (config files are code — a broken or hostile one degrades to defaults plus a warning), and written by `lib/serialize` with stable key order for clean diffs.
- **Defaults merge:** user values win; default keys the user has never seen are added; keys the defaults do not mention (user-created layout slots) are preserved.
- **Character scoping:** the character name is unknown until login, so components are attached on login and detached on logout, and nothing renders while logged out. Core scopes on the **name alone** — anything else a component needs from the client it waits for itself, because the client fills the player in field by field and no single field vouches for the rest (see `parambar` below). The `login` event is a one-shot that can fire before `get_player()` can name the player, so `on_prerender` keeps looking: every 0.05s while the client says we are logged in, every 1s at character select, re-armed by each login event. A login that cannot be resolved leaves the character already scoped alone — dropping one is the logout's job — and keeps the search running, so logging in as someone else without a logout event still switches.
- **Layout slots:** position, scale and visibility live under named slots — `slots = { default = { pos = {x, y}, scale = 1, visible = true } }`, or `slots = { default = { anchors = { <name> = { pos = , scale = } }, visible = true } }` for a multi-anchor widget. `default` always exists and cannot be deleted. Slot names are matched case-insensitively and stored lowercase. The set of slots is the union across components; the active slot name is in core's config, and every layout write persists into it immediately. A component with no entry for a slot falls back to its default layout.
- **`//hud copy <source> <destination>`** replaces the destination's `data/<Character>/` tree with the source's: the destination is emptied first, so what remains is the source's configuration and nothing else. Both ends are named explicitly, so it does not depend on who is logged in, and it reloads only when the destination is the character being played. It is destructive and has no undo and no confirmation step.

## Commands

`//hud` (alias `//xivhud`). Verbs and component names match case-insensitively; unknown input always answers with a hint, never silence.

```
//hud | //hud help              -- command list
//hud layout | setup           -- toggle layout mode
//hud list                     -- components with state, position and scale
//hud show|hide <component>
//hud reset <component|all>    -- restores defaults, which drops that component's named slots
//hud slot <name>              -- switch layout slot
//hud slot list|create <name>|delete <name>
//hud copy <source> <destination> -- replace the destination's config with the source's
//hud <component> [...]        -- passthrough to the component's handle_command
```

Party list, on each of `partylist` / `alliancelist1` / `alliancelist2` (`hidesolo` and
every `buff` verb are `partylist` only):

```
//hud partylist spacing <px> | align top|bottom | emptyrows on|off | hidesolo on|off
//hud partylist range num|icons | range <near> <far>
//hud partylist buff                     -- the icon slots that actually get drawn
//hud partylist buff list [page] | find <text> | active [<member>]
//hud partylist buff top|up|down <id|name> | rank <id|name> <n> | reset
//hud partylist buff filter add|remove|clear|list [<id|name>] | filter mode blacklist|whitelist
```

Every verb that *shows* buffs deliberately reaches past the icon cap: only the first
twelve are ever drawn, so a buff you cannot see is a buff you cannot promote.

Target bar:

```
//hud targetbar                  -- the range mode in force
//hud targetbar mode auto|default|magic|ninjutsu|gun|bow|xbow
```

`auto` follows the main job (casters get `magic`, NIN `ninjutsu`, COR `gun`).
RNG deliberately lands on `default` and is told to pick a weapon: nothing in the
client says which one is equipped.

Equip viewer:

```
//hud equipviewer                        -- both toggles as they stand
//hud equipviewer encumbrance on|off
//hud equipviewer ammocount on|off
```

Crossbar (the widget answers `set`, bare `cycle`, bare `open`, `edit` and the
built-in actions itself; `commands.lua` answers the rest):

```
//hud crossbar                           -- job, active set, and where each view points
//hud crossbar help
//hud crossbar set <1-8> | cycle | list [<set>] | wxhb [on|off] | retry [on|off]
//hud crossbar bind <address> <type> [<action>] [<target>]
//hud crossbar unbind|alias|icon <address> [...]
//hud crossbar swap <address> <address>
//hud crossbar view <wxhb-L|wxhb-R|exp-LR|exp-RL> <set><L|R>
//hud crossbar share <set> on|off
//hud crossbar cycle <set> drawn|sheathed|both|none
//hud crossbar copy <JOB> | context list | open [<name>]
//hud crossbar draw | mr | warp [all] | edit
```

An **address** is one word, `<set><L|R><slot>` - `1L1`, `2R8` - and takes the
layer prefixes `sub:` and `ctx:<name>:` in front on the four verbs that write
one layer. It was three words (`1 l 1`) until 2026-08-22: a lower-case `l`
beside digits is indistinguishable from a `1` in the game's font, so the side
is written upper case (either case parses) and the three words are one, which
cannot be miscounted either. The slots' controller names went at the same time
- there is no controller for them to name - so a slot is 1-8 and nothing
else.
Two verbs are deliberately overloaded: bare `cycle` advances the rotation while
`cycle <set> <mode>` edits membership, and bare `open` lists the screens while
`open <name>` opens one.

In layout mode: left-drag moves a widget (snapped to the grid; hold CTRL for free movement), the wheel scales it (floor 0.25), right-click toggles it on or off. A multi-anchor widget drags and scales one anchor at a time — the one under the cursor — while the right-click still toggles the whole widget. Every change persists immediately. Auto-hide outranks layout mode: the HUD stays hidden during a cutscene (player status 4, disable with `hideCutscene`), while zoning (plus a ~3s settle), and while logged out.

## Components

- **`partylist` / `alliancelist1` / `alliancelist2`** (`src/components/partylist/`) — the FFXIV party list: the main party and both alliance parties, each independently positioned, re-implemented from [XIVParty](https://github.com/Tylas11/XivParty) 2.2.0. One factory registered three times; `ctx.variant` picks the party keys (`p0..p5` / `a10..a15` / `a20..a25`) and which of the two row layouts to draw. `logic.lua` is the pure state machine (roster, bars, colour bands, distance dimming, buff ordering, the command parser, the layout-mode preview); `packets.lua` parses `0x0C8` / `0x0DD` / `0x0DF` / `0x076`; `layout.lua` is the hardcoded `xiv` geometry; `buff_order.lua` and `jobs.lua` are ported data. `partylist.lua` owns the prims and builds a row's set only when that row is occupied. Buff settings belong to `partylist` alone — `0x076` carries the main party only, and the alliance row has no buff icons. `assets/` holds XIVParty's `xiv` art, redistributed under the BSD 3-clause notice in `assets/LICENSE.txt` (© 2024 Tylas).
- **`parambar`** (`src/components/parambar/`) — the FFXIV parameter bar: HP/MP/TP fills with numbers, re-implemented from XIVBar. `logic.lua` is the pure state machine (easing, colour bands, layout maths, its command parser); `parambar.lua` owns the prims. `assets/` holds XIVBar's `ffxiv` theme art, redistributed under the BSD 3-clause notice in `assets/LICENSE.txt` (© 2017 SirEdeonX) — that file ships with the addon. Commands: `//hud parambar [width|spacing|offset <px> | compact on|off]`. **Vitals arrive piecemeal.** The client fills `get_player().vitals` in field by field: in a live client HP landed while MP was still 0, and because the `hp change`-style events only fire on an actual *change*, a single seed at attach left the MP bar reading 0 until the player cast a spell. So parambar re-reads the player each frame after attaching and fills in only the vitals the client has never given a number for - a vital an event has spoken for, including one it drove *to* zero (death, an empty MP pool), is left where the event put it. The reading stops as soon as every vital is known, or after ten seconds, whichever comes first. Waiting for the whole table instead is not available: `max_mp` is legitimately 0 on a job without MP.
- **`targetbar`** (`src/components/targetbar/`) — the current target's health bar: a `HP% | distance | name` row above a bar drawn on the same XIVParty `xiv` art the party list uses, re-implemented from the Windower `enemybar` addon with [DistancePlus](https://github.com/Windower/Lua/tree/dev/addons/DistancePlus)' range colouring. `logic.lua` is the pure state machine (ease, claim state, hp bands, range bands, the command parser, layout maths); `targetbar.lua` owns the prims. `assets/xiv/` holds partylist's three bar textures **regenerated at two widths** (4x for the health bar, 2x for the cast bar) under its own `assets/LICENSE.txt` (© 2024 Tylas) — a component owns everything it draws, so nothing here reaches into a sibling's directory. **Three colour channels, deliberately independent**: the hp number bands (partylist's `< 25 / < 50 / < 75`), the distance follows DistancePlus' job-aware bands, and the **bar fill carries enemybar's six-state claim palette** — moved off the text, where the reference put them, onto the fill, with one colour changed: claimed-by-us is deepened to `255,20,20`, because the reference's pale pink was picked for text and washes out across a fill. Two fixes over the reference's `check_claim`: the ownership set is the whole **alliance** (it only scanned `p1`–`p5`), and an **unclaimed mob is never "mine"** — the reference initialises its player id to `0` and compares it to `claim_id`, so before the player resolves it paints every free mob as claimed by you. The roster and the player ride a 200ms poll (partylist's cadence); only the target itself is read per frame. **The bar frame draws at 512x64, from art regenerated for that width** — never by stretching the texture at runtime, which would warp the bevelled caps. The source art's middle is a run of identical columns, so the wide version preserves both caps byte for byte and extends the middle by replicating the centre column: no pixel is interpolated (the same move as partylist's regenerated row panel; transform documented in `assets/LICENSE.txt`). Only the fill inside the frame is stretched at runtime, to the health percentage. The framework's uniform scale is the only way to resize the widget, and all vertical placement is measured from the visible band at drawn y 25..39 (texture rows 50..77 at 2x) rather than the art's own top, which is 25px of transparent padding that would otherwise draw above the origin. **The cast bar**: a smaller second bar (its own half-width art drawn at 0.67, about a third of the health bar), right-aligned under the first with the spell or TP-move name beneath it, raised while the target winds something up. It rides the existing `incoming chunk` dispatch - the `0x028` action packet, which reaches the widget already decoded by **`windower.packets.parse_action`** in the entry point (core API, used the same way by GearSwap/Debuffed/enemybar2; the `action` *event* is deprecated and deliberately not used), since the crossbar's skillchain engine reads the same packet and one decode serves both. Spell fills run against `res.spells[].cast_time` (seconds); TP moves have no duration in any packet or resource, so theirs is a fixed `tp_move_sweep` animation. Interrupts are structural - a start-shaped packet whose one action has `message == 0` aimed back at the caster - and every bar carries a duration+grace expiry besides, so a finish the stream never delivers still clears. Without the resources library the cast feature alone sits out (no names to show); the rest of the widget carries on.
- **`equipviewer`** (`src/components/equipviewer/`) - the equipped gear grid: sixteen item icons in the reference's 4x4 arrangement, an X over any slot encumbrance has locked, and the ammo count over the ammo icon, re-implemented from the Windower `equipviewer` addon (© 2021 Tako/Rubenator). `logic.lua` is the pure state machine (what is in each slot, the encumbrance decode, the ammo count, layout maths, its command parser); the pure half of the icon extraction lives in `lib/icons` and the queue-and-cache discipline around it in `lib/icon_cache`, promoted out of this component so the crossbar can draw item art without requiring a sibling (CLAUDE.md forbids that outright, and duplicating the byte-level DAT parsing is exactly what the isolation rule exists to prevent); the Rubenator notice travels with the code. `equipviewer.lua` owns the prims and the io. **No icons ship with the addon** - there are tens of thousands of items and the art is the game's, so the first time an item is seen its icon is read out of the client's own `ROM/*.DAT` files, decoded and cached as a bitmap under `icons/` beside the addon (shared across characters, gitignored and stripped from the package). It is deliberately **not** under `data/`: `//hud copy` enumerates every directory there as a character, so a cache alongside them would be offered as one and `//hud copy icons <character>` would wipe that character's configuration. The record is a 256-colour palette plus one index byte per pixel, every byte of it bit-rotated (`(i % 32) * 8 + floor(i / 32)`) with alpha stored at half scale; `icons.to_bmp` un-rotates the palette only - 256 entries, not 1024 pixels - and expands the pixels through it in one `gsub`. Two oddities of the reference's header are kept deliberately: the colour space is written as the literal `sRGB` (the LCS_sRGB constant byte-reversed) and the height is positive, so rows read bottom-up. **Extraction is queued, one icon per frame**, never done where the packet arrives: a first login with nothing cached would otherwise mean sixteen DAT opens, decodes and file writes inside a single frame. An item that fails is abandoned for the session rather than retried every frame — behaviour that now lives in `lib/icon_cache` and is shared with the crossbar, one `<addon>/icons/` directory between them, so an item either component has extracted is never extracted again. The game path is `windower.ffxi_path` (undocumented - the wiki has `pol_path`), falling back to `pol_path`, with a `game_path` setting overriding both. The write goes through the entry point's `write_binary`, which opens `"wb"`: the existing `write_file` uses text mode, and on Windows that would turn every `0x0A` byte of a bitmap into `0x0D 0x0A`. Encumbrance is decoded with arithmetic rather than LuaJIT's `bit`, which is not part of Lua 5.1 and could not be tested here. Deviations from the reference: position, scale and visibility are framework-owned (its `pos`/`size`/`scale`/`justify` verbs are gone), so are `hide_on_zone` and `hide_on_cutscene`; the ammo count is left-justified for the same reason giltracker's number is; the equipment table is read once per refresh rather than once per slot; a job change is caught on `0x01B` rather than by registering an outgoing chunk handler that would see every packet the client sends. `assets/encumbrance.png` is redistributed under the BSD 3-clause notice in `assets/LICENSE.txt` (© 2021 Rubenator, base extraction code credited to Trv); `assets/panel.png` is XIVHud's own white square, tinted for the panel behind the grid.
- **`giltracker`** (`src/components/giltracker/`) — the FFXIV gil widget: the current gil total beside the gil icon, re-implemented from the `giltracker` addon. `logic.lua` is the pure state machine (when a re-read is warranted, formatting, layout maths); `giltracker.lua` owns the prims. `assets/gil.png` is redistributed under the BSD 3-clause notice in `assets/LICENSE.txt` (© 2017 sylandro) — that file ships with the addon. No commands. **Gil is never polled**: `windower.ffxi.get_items()` pushes every item the character owns and nothing cheaper carries gil, so the entry point forwards `incoming chunk` plus `add item`/`remove item` and the component reads only when a packet says gil may have moved. The number is left-justified inside a width reserved for the 999,999,999 cap, which keeps the icon still as digits change and lets `get_bounds` return the same origin `set_pos` was given.
- **`crossbar`** (`src/components/crossbar/`) - the FFXIV Cross Hotbar: sixteen slots drawn as two four-button crosses, raised by holding a side key, over eight sets and three bars (the XHB, the WXHB's two halves, and Expanded Hold on both side keys at once), re-implemented from the Windower `xivcrossbar` addon (MIT (c) 2020 AliekberFFXI; per-file BSD (c) 2017 SirEdeonX, inherited from `xivhotbar`). By far the largest component, and the only one that uses all three framework touchpoints it drove: four **anchors** (`main`, the WXHB's two independently placed halves, and the skillchain `indicator`), `wants_store` for per-job bindings (`data/<Character>/crossbar/<MAIN>.lua`, plus `SHARED.lua` for the sets flagged shared), and both `on_keyboard` and `on_mouse`. `input.lua` is the pure DIK state machine (hold states, the switch chord, the block verdict); `bindings.lua` the layer stack (buff contexts over subjob overrides over the job base or the shared store); `render.lua` the geometry and the draw plan; `commands.lua` the authoring CLI, `binder.lua` the mouse binder over `catalog.lua`; `actions.lua`, `openers.lua`, `roulette.lua`, `warp.lua`, `enchanted.lua`, `enchanteditem.lua`, `counters.lua` and `skillchain.lua` the bindable behaviour - `enchanteditem` is the `enchanteditem` bind type, warp's ladder with the ladder taken out: one named piece of gear searched for across every equippable bag (`enchanted.candidates`, which answers EVERY copy ranked - reachable first, then the one on your hand, then bag order - so a spent ring on your finger cannot hide a charged spare in your bag; `enchanted.collect` is the one-winner form beside it, which the warp ladder uses and which deliberately has no worn preference for that same reason), resolved into the same three plan shapes so **one** scheduler in the widget runs either and the two cannot drift. That scheduler CHECKS THE PIECE ACTUALLY WENT ON before reading anything off it, and puts it back when it has not: `gs disable` stops future GearSwap swaps but cannot cancel one already in flight, so a set equipped in the same breath as the press lands on top of ours and the ring never reaches a finger - after which the extdata being polled belongs to a ring in the bag, and the use branch would fire `/item` at something not worn (refused by the game, and broadcast on by `warp all` regardless). It re-issues once a poll until the deadline rather than giving up early, since a GearSwap burst can outlast several seconds. It takes **no** travel countdown - the warmup already is the wait - and only one wait of any kind is ever in flight, so a pending warp blocks an enchanted item and the reverse. A deferred use **resolves its target at the press**, the way the cast retry does: the command goes when the enchantment comes up, so a `<t>` carried that far would land on whatever had been tabbed to since. A token the press cannot resolve - `<st>`, or `<t>` with nothing selected - is refused before any GearSwap slot is held, rather than deferred and resolved late. A slot bound to either `item` or `enchanteditem` also carries a **count** in its corner (`counters.item_display`: what the bag holds, capped at `99+`, drawn in plain white - no master-tool substitution and no colour bands, both of which are ninja-tool facts rather than item ones). Zero raises the red X and dims the slot **only where the zero is trustworthy**: gear always, a plain item only once a bag whose name contains `temporary` has been found, since a name miss there would otherwise cross out a press that works - a missing warning being the better failure. The bag re-read that feeds it is gated on the ids some painted slot is actually bound to, so an unrelated item moving costs nothing, and a **repaint** re-derives the set of bound ids and marks it dirty only when that set actually CHANGED - but `add item`/`remove item` fire only when a record ENTERS OR LEAVES a bag, so a decrement within a stack (four of five left) reached the count only when it emptied; the decrement rides the `0x01E` Modify Inventory packet instead, which the component already receives and which carries no item id, so it is gated on whether any painted slot draws a bag-fed number at all and coalesced by the same dirty flag - a bind or a context flip usually does, a hold state or a same-contents set switch does not, and marking every repaint dirty would re-read up to ten bags for nothing. Where it counts from differs by type and deliberately so: a consumable from the **inventory and the Temporary bag** (a potion in a wardrobe is not one the game will let you drink, but an item held temporarily is one `/item` can use - the bag is found by name, never by a remembered id, and read only when something is bound to an item id). Note the ladder does not share that scope - `enchanted.collect` walks equippable bags only - which is harmless for its own rungs, Instant Warp being an ordinary inventory item (confirmed 2026-08-21). Gear counts from every equippable bag; `retry.lua` the cast retry, which re-sends ONE refused action - a spell, job ability or weaponskill, each keyed to its own refusal message and its own blocking buffs (silence/mute stop spells, amnesia stops the other two) - reactive, never predictive (it reads the refusal off the `0x29` the component already receives, so a press the game accepted is never delayed), it **never holds an action blocked by a recast** (the defect that made the reference addon's queue unusable), and it **pins the target at the press** and re-sends the mob id in place of `<t>`, so a retry cannot wander onto whatever you have since tabbed to; `travel.lua` the travel delay, which holds `mount`, `mr` and `warp` for a configurable `delay` (5s, zero to switch it off) and counts it out in chat - the opening line names the RUNG (`Warp Ring in 5 seconds`, not a bare `Warp`: the ladder has several and the player is about to spend one) and only the last five seconds are spoken, since a warm-up's thirty would be a wall of text. A ring **warm-up** is narrated too, by the poll that owns its clock rather than a second one armed beside it: which item at the press, its length once the extdata can be read, then the last five - and resting calls it off like any other trip, releasing the GearSwap hold, which it never used to. The ladder is walked ONCE, so the rung announced is the rung that fires: resting cancels it - the trigger is the player STATUS, resolved from `res.statuses` by english name rather than hardcoded, so an unconfirmed fallback constant is only reached without the resources library - and so do the transitions that end any other moment (zone, death, logout, job change, suppression). Getting OUT of something is never held: mount roulette's dismount, a NAMED mount slot pressed while mounted (which dismounts rather than sending its summon - the two used to disagree, so the same press was instant on one slot and a five-second countdown on the next) and `draw` stay instant, and a warp skips the countdown when the rung it picks must be **equipped and warmed up** first - that wait already is the window, and the condition is the wait rather than the item, so an already-equipped charged ring counts down like a spell. `warp all`'s IPC broadcast rides the moment the LOCAL warp commits - the send for a spell or a charged item, the deferred use for a ring being warmed up, at once when the ladder found nothing - so neither a cancelled countdown nor an abandoned warm-up leaves the alts already sent home. **Opening a config mode ends a trip too**: `//hud layout` and the binder cancel one that is counting down and refuse one pressed while they are open (a late action fires only where a fresh press would - CB9's rule; an open chat line is deliberately not one of these, unlike the retry), and a re-attach - `//hud reset crossbar`, and the reload after `//hud copy` - drops one too, since the configuration that armed it has just been replaced: the COUNTDOWN goes silently, a warm-up says `warp dropped - <item>` and releases its GearSwap hold, because a ring left on your finger with nothing coming is not something to work out from silence. A job change, a death, a zone and an opened config mode all end both halves - the last of those BEFORE the poll that would otherwise fire the very trip being called off. `crossbar.lua` owns the prims, the io and every `ctx` read. **There is no gamepad** — Windower cannot see one, so the bar reads keys and a Steam Input layout presses them for the player — and for the same reason **no modifier is used**: `return true` swallows a bare key completely but does not stop FFXI acting on a Ctrl/Alt chord (verified in-client, after two input designs died on that fact), and the game's own macro palette lives on exactly those chords. The five punctuation keys (`;` `'` `\` `` ` `` `=`) are the component's outright; the number row is the game's except while a hold state or the switch is up. **Weapon state is the component's own state machine**, never the client's status: `draw` toggles it, engaging in game also enters drawn, and a mob dying does not leave it - so the cycle rotation cannot lurch back mid-pull. A slot draws at most ten characters of its action's name, with a `.` on the end where it was cut - the stored record keeps the whole name, which is what `//hud crossbar list` prints and what the game is sent, and the edit-mode source mark is added after the cut so a slot reads the same either way. The active set is written between the two crosses in parambar's size and gold, with a sword stacked above it while the weapon state is DRAWN (the component's own state, so it lights on `draw` even with nothing targeted) - so a set switch is visible on a bar with nothing bound to it, which is how its absence was found in a live client. Both are centred on the bar independently and the label's foot is aligned with the BOTTOM slot row's foot: in the middle row the two clusters occupy the bar's centre column, so anything drawn level with it lands on the art, which is exactly what the first attempt did. **The resting inventory is 365 prims - 244 images and 121 texts - constructed in the factory, at `core.register` time and so before login, and merely hidden** (a set switch repaints existing prims rather than allocating more), which is a resting cost only a live client can price; destroy-when-off is the fallback and is confined to the widget's build/refresh. Edit mode sits on top of that and is never resident: the binder builds its own window and rows when it opens and destroys them when it closes. It is **one** window - 920x600 at 18pt, dead centre, opened by clicking a slot and walking three steps (layer, then action, then target for the types that take one), with a back button that walks them in reverse and closes from the first, and a details column where the floating tooltip used to be. Three surfaces beside one another was the first design and failed in a live client: the stack panel opened beside its slot and drew UNDER the neighbouring slots' labels, and Windower renders every `texts` object above every `images` one, so no creation order could lift a backdrop clear of them. Item icons come from the shared `lib/icon_cache`; the ~1,300 shipped icons are load-checked by sampling, the party list's convention. Defects of the reference deliberately not reproduced: it `unbind`s `^f1`-`^f12` at load and never restores them (this takes no keybind at all), its bind is a non-atomic remove-then-insert that can lose the original, its no-target actions emit an unterminated quote, and its catalog gates a spell on `levels[job] <= job_level` - which **a merit spell can never satisfy**, since it encodes its requirement as a sentinel far above the cap (Refresh III at 1200), the defect that drove this port off the reference fork. Ours includes a known action whose requirement is above the cap when the job in question is the **main** one, because merits and job points apply to the main job alone (the same rule the stratagem gift follows). `skillchain.lua` transcribes the property and chain-resolution tables from the `SkillChains` addon (BSD, (c) 2017 Ivaar) and is fed parsed `0x028` packets by the widget rather than listening itself; the imported icon pack and UI art carry their notices in `assets/LICENSE.txt`.

## Packaging & releases

[.github/workflows/package.yml](.github/workflows/package.yml) builds the distributable zip. It runs on pushes to `main` and `rc/**`, and on `v*` tags.

- **What it produces.** Everything in `src/` is copied into a single top-level folder **named after the repository**, then zipped (`XIVHud/…`). A user unzips it into `Windower4/addons/`, yielding `addons/XIVHud/`. The runtime `data/` dir is stripped from the package.
- **Folder/main-file rule.** Because the folder is the repo name, the main file must be `src/XIVHud.lua`, or Windower won't load it. The "Check source" step emits a `::warning::` when that file is missing — treat that warning as a real defect, not noise.
- **Delivery.** Branch pushes (`main`, `rc/**`) upload the zip as a **workflow artifact** (ephemeral). Pushing a `vX.Y.Z` tag additionally creates a **GitHub Release** with the zip attached (a semver pre-release tag like `v1.2.0-rc.1` is marked pre-release). Releases need `contents: write`, already granted in the workflow.
- **Build outputs** (`dist/`, `*.zip`) are gitignored.

## Line endings (important)

`.gitattributes` enforces **CRLF in the working tree** (`* text=auto eol=crlf`) because this targets Windows/Windower; git still stores LF-normalized blobs, so diffs stay clean. The sole exception is `.devcontainer/Dockerfile`, which is forced to LF for the Linux container. Don't fight the CRLF checkout — it's intentional.
