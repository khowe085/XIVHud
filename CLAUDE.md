# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

**XIVHud** — a **Windower 4 addon** for Final Fantasy XI, written in **Lua 5.1**: a configurable HUD framework of composable widgets designed to work in the style of Final Fantasy XIV's HUD system, arranged through the addon's settings rather than one fixed display. Windower is a Windows-only launcher/injection platform that loads addons at runtime and exposes them a global API. The addon's source lives in **`src/`**; a GitHub Action packages it into a zip that users unzip straight into their Windower `addons/` directory (see Packaging & releases below).

Because addons run inside Windower on Windows, they cannot be executed or fully tested in this Linux devcontainer. Development here is authoring, linting, and formatting; runtime verification happens in a live Windower/FFXI client on Windows.

## Toolchain & commands

The devcontainer (Alpine) provides Lua 5.1, luacheck, StyLua, busted, and the GitHub CLI.

- **Test:** `busted` — runs every `*_spec.lua` under `tests/`, including `tests/components/` (config in `.busted`). Filter with `busted tests/core_spec.lua` or `busted --filter "layout"`.
- **Lint:** `luacheck .` — config in `.luacheckrc` (std `lua51`). luacheck auto-applies its `busted` std to `*_spec.lua`, so `describe`/`it`/`assert` need no whitelist.
- **Format:** `stylua .` (or `stylua --check .`) — config in `stylua.toml` (2-space indent). Also runs on save in VS Code via the StyLua extension.
- **Run a script standalone:** `lua <file>` — only for pure Lua with no Windower globals; anything touching the addon API must run inside Windower.

There is no build step. "Passing" locally means green `busted` + clean `luacheck` + `stylua --check`.

**Green locally does not mean it loads.** Nothing here exercises `require` resolution inside Windower, the real `texts`/`images`/`files` libraries, or the prim layer — and this addon has already shipped a build that passed every check and then failed to register a single event in the client. Treat any claim about the Windower API as unverified until it is read in the [library sources](https://github.com/Windower/Lua/tree/dev/addons/libs) or confirmed in a live client; the wiki documents what a function returns far more often than how it behaves at the edges.

## Windower addon conventions

These are platform facts about how Windower loads and runs addons:

- **Globals in `.luacheckrc`.** The whitelisted globals are `windower`, `texts`, `images`, `res`, `packets`, `_addon`. (`files` is deliberately absent — see the file I/O note below.) Two kinds are mixed here:
  - *Truly injected by Windower:* `windower` (core API — events, chat, packet send, ffxi/player/target data) and `_addon` (addon metadata: name, version, author, commands).
  - *Libraries assigned to globals by convention:* `texts`/`images`/`res`/`packets` are loaded with `require('texts')` / `require('images')` / `require('resources')` / `require('packets')` and conventionally stored in a same-named global; `files` similarly wraps addon-relative file I/O. See the Libraries wiki below. When you introduce a new global, register it in `.luacheckrc` so luacheck stays clean.
- **Addon layout.** Installed, an addon is a folder under `Windower4/addons/` whose main `.lua` **must share the folder's name** (Windower loads `addons/<folder>/<folder>.lua`). Here the source lives in `src/` and the packaging step wraps it in a folder named after the repository — so the main file is **`src/XIVHud.lua`** (the Action warns if it's missing). The main file declares metadata on the injected `_addon` table: `_addon.name`, `_addon.author`, `_addon.version`, and its commands. **The convention is `_addon.commands`, listing the primary name first** — of roughly forty addons in the Windower repository, all but one set either `_addon.command` (a single name) or `_addon.commands` (a list), never both. This addon currently sets both, which is redundant: it was added while chasing an addon that answered no commands at all, and the cause of that turned out to be elsewhere entirely, so which field Windower honours was never actually established. Reducing it to `_addon.commands` alone needs a live client to confirm `//hud` still routes. At runtime, user settings live under `<addon>/data/` — generated by the addon, never committed (gitignored, and stripped from the package); see Settings below for the per-component scheme this repo uses instead of a single `settings.xml`. Every source file carries the **BSD 3-clause license header** (Windower convention — © 2026, Azureblood2).
- **Settings.** This repo does **not** use Windower's `config` library — see Settings below. (For reference, the platform convention is `settings = config.load(T{...})` then `settings:save()`; `config` can only serialize XML, and the character name is not known until login, neither of which fits the per-component scheme here.)
- **Events.** Behavior is driven by handlers registered with `windower.register_event(...)`. Common events: `'load'`, `'unload'`, `'addon command'` (from the addon's command), `'incoming text'` / `'outgoing text'`, `'incoming chunk'` / `'outgoing chunk'` (packets), `'prerender'` / `'postrender'`, `'login'` / `'logout'`, `'zone change'`, `'status change'`. Text/chunk events may return modified data or a block flag.
- **Common libraries** (`require(...)`): `config` (Windower-XML settings load/save), `logger`, `tables`/`strings`/`sets`/`lists`/`functions` (data-structure & functional helpers), `resources`, `packets`, `texts`, `images`, `json`, `chat`. See the Libraries reference below.
- **Gotchas that cause real bugs** (fuller treatment in the mirrored Lua guide below):
  - `windower.ffxi.get_player()` / `get_mob_by_index()` can return `nil` (not logged in, index not loaded) — guard before indexing. A PC has both a permanent ID and a per-zone **mob index**; use `target_index`/index for in-zone lookups.
  - Windower and Lua **fail silently**: too few/many function args yield `nil`/dropped values, and undefined table keys return `nil`, all without erroring. A `nil` in an array also halts `ipairs`/`#` iteration early. Validate inputs yourself.
  - Tables are **1-indexed**; there's no built-in string split or table slice (use `strings`/`tables`). `T{}` (from `tables`) is needed for method-style calls like `t:map(...)`; convert the mob/player arrays with `T(...)`.
- **Library setters that are also getters** (verified against the `dev` sources; each cost real debugging):
  - `texts`/`images` accessors return the current value when called with **no argument**. `text:right_justified()` does not right-justify — it *reads* the flag. Always pass the value: `text:right_justified(true)`.
  - `stroke_transparency` and `transparency` take **0..1**, and internally compute `alpha = 255 * (1 - value)`. Passing a 0–255 alpha to them produces a wildly negative alpha. Use `stroke_alpha`/`alpha` for 0–255.
  - The guards are `if not x` / `x == nil`, and **`0` is truthy in Lua**, so a numeric zero is *not* mistaken for "no argument". `color(0, g, b)` and `stroke_width(0)` behave.
  - `image:fit(true)` sizes a prim to its texture, which defeats explicit `size()`. Anything scaled or stretched must set `fit(false)`.
- **Do not write config through the `files` library.** Reading its source suggests `files.new(path):write(contents)` creates any missing directories (`write` → `create()` → `create_path()` → `windower.create_dir`), and that reading is what this repo originally relied on — but `files.create` **ignores the error from `create_path`** and then indexes the nil handle from `io.open`. In practice that printed `New file: data/…` and produced no file, for days. `src/XIVHud.lua` builds each directory itself with `windower.create_dir`, checks the result, re-checks with `dir_exists` (success can be reported for a directory that is not there), and writes with plain `io.open`. Raw `io` against `windower.addon_path` is the one file operation proven to work here.
- **Other I/O facts** (verified): `windower.get_dir(path)` returns files and directories together, so classify entries with `windower.dir_exists`. A texture path that does not exist fails **silently** — the prim simply draws nothing.
- **Never shell out.** The addon runs inside the game process, so `os.execute` and `io.popen` flash a console window over the client. Every file operation here calls straight into the C library instead: `io.open` for reading and writing, `os.remove` for deletion — none of which create a process. `tests/sources_spec.lua` fails the build on a process-spawning call in `src/`.
- **Chat is not UTF-8.** Anything passed to `windower.add_to_chat` must be plain ASCII: an em dash reaches the player as `â€”`. Write `-` in user-facing strings, never `—`. Comments are exempt — they are never displayed, and the licence headers keep their `©`. `tests/sources_spec.lua` fails the build on a non-ASCII byte outside a comment.
- **`src/XIVHud.lua` traces its own load** to `<addon>/load.log` with raw `io` — every load step, `addon_path`, and the result of each `create_dir`. An empty file named `safe_mode` beside it loads the framework and commands but no component or render loop, which is the bisect to reach for when the client misbehaves. Both are load-time only and deliberately kept: an addon whose chunk dies is silent, and a client that then crashes takes the console with it. **Nothing traces from the render loop** — a heartbeat there found a crash once and was removed the same day, because per-frame disk I/O is not something to ship.

## Modular design & testing

Addons are structured so the logic is unit-testable **without a running Windower client**, using **dependency injection**. The rule: pure logic never touches Windower globals directly — it receives what it needs as a `deps` table.

```
src/
  XIVHud.lua              -- entry point: the ONLY file that reads Windower globals
  lib/                    -- the framework; pure, factory style `new(deps) -> instance`
    core.lua              -- orchestration: registry + settings + visibility + layout mode + commands
    registry.lua          -- component registration, enumeration, teardown
    settings.lua          -- per-component config service (data/<Character>/<slot>/<component>/)
    serialize.lua         -- Lua-literal serializer with stable key order
    commands.lua          -- `//hud` parser -> action tables
    layout.lua            -- snap/clamp maths and the repair of a layout table
    layout_mode.lua       -- `//hud layout` drag/scale/toggle state machine
    overlay.lua           -- layout-mode highlight box + name label per component
    visibility.lua        -- auto-hide suppression resolver
    icons.lua             -- pure item-icon extraction (DAT record -> bitmap)
    icon_cache.lua        -- the queue/cache discipline around it, shared by components
    player.lua            -- one read of the client per interval, shared by every component
  assets/                 -- ALL bundled art, grouped by where it came from
    own/                  -- XIVHud's own art (overlay.png among it), and xivcrossbar's chrome
    icons/                -- the ~1,300 action icons, plus jobs/: the party
                             list's job icon stack pre-composited flat on a
                             SOLID role colour, at the source's own 64x64 so
                             a 40x40 slot scales down rather than up. Its own
                             art and its own notice (generated, not
                             hand-drawn - see icons/jobs/LICENSE.txt)
    cooldown/             -- the radial recast frames
    xiv/                  -- XivParty art (+ jobIcons/, buffIcons/, wide/)
    ffxiv/ gil/ encumbrance/ -- XIVBar, giltracker and equipviewer art
    barfiller/            -- barfiller's 472x5 bar frame and its 1px fill
  components/<name>/      -- ALL of a component's CODE, isolated per component
tests/
  *_spec.lua              -- one spec per lib module
  components/*_spec.lua   -- component specs, mirroring src/components/
  support/fakes.lua       -- fake deps, file system, prim recorder, widget
```

- **Pure modules (`src/lib/`).** Each returns a constructor `new(deps)`. It calls `deps.get_player()` etc. — never `windower.*` directly. Because deps are plain functions, a test "mock" is just a table of stubs; no mocking framework required.
- **Entry point (`src/XIVHud.lua`).** The only place that reads globals. It builds the real `deps` from the live API, wraps Windower's method-style prims (`t:pos(x, y)`) as plain function tables for components, constructs and registers each component, and wires `windower.register_event(...)`. Packets are pushed the same way: every `incoming chunk` is dispatched to every component as `update('chunk', id, original, parsed)`, and a component decides for itself, from the id alone, whether it is worth reading -- giltracker's own `logic.wants_chunk` does exactly that for item packets. `parsed` is non-nil only for the ids with more than one reader, which the entry point decodes **once** rather than once per consumer: the three party-list ids Windower has a field definition for (`packets.parse`, rather than once per sibling list), and the `0x028` action packet (`windower.packets.parse_action` — core API, not the `packets` library), wanted by targetbar's cast bar and the crossbar's skillchain engine, which parsed it one apiece until CB6. Both parses are `pcall`'d, so `parsed` is also nil when the decode failed, and the raw bytes always ride alongside it — a component that wants its own decode still has them. A fourth id the party list reads, and everything giltracker cares about, has no such definition and is decoded from the raw bytes by the component itself. `core.dispatch` walks every registered component regardless, so a component that does not want packets has to ignore the event rather than be spared it. Item movement is pushed too, narrower: `add item`/`remove item` dispatch as `update('add item'|'remove item', id)`. `gain focus`/`lose focus`, `gain buff`/`lose buff`, `job change` and `ipc message` are forwarded whole under their own names for the crossbar (input reset on alt-tab, context layers, the per-job binding reload, `warp all`). It also builds the **player service** (`lib/player`) over the four client reads and hands every ctx *its* getters rather than the raw calls, so a component cannot reach past it: `begin_frame` runs at the top of `prerender` before core touches anything, the vitals events feed `set_vital` on the way to `core.dispatch`, and `zone change` / `login` call `invalidate()` and so does `logout`; **core announces a scope change through `deps.on_scope_change`, which invalidates too** - core scopes from its own prerender search rather than from the `login` event, and between the two the outgoing character's components are still attached and still reading, so the event alone would let the incoming character's first tick read the outgoing one. Announced BEFORE the attach, for that reason. Meanwhile `status change` / `job change` / `gain buff` / `lose buff` call the keyed `invalidate("player")` - none of those three changes the party or the zone, and buff events are frequent enough that dropping the whole interval for one would undo the deduplication. A keyed invalidation deliberately does **not** move the counter, or it would put the party list through a full roster rebuild for a fact it does not hold. An unknown key drops everything rather than nothing: a typo must not quietly become a no-op. The last three are there because a component answers them straight out of `get_player()` the moment they arrive - the crossbar diffs `player.buffs` once, from the event, so a list read before the buff landed would diff to no change and leave a context layer wrong until the next buff event. Keep it thin — anything worth testing belongs in `lib/` or a component.
- **Component isolation.** A component's whole implementation lives in `src/components/<name>/`, entry file `<name>.lua`. **Art is the exception, and moved out on 2026-08-24**: every bundled image lives under `src/assets/`, grouped by PROVENANCE rather than by consumer, so a component may draw from any of it and each upstream's notice sits beside its own files. That replaces the older "a component owns everything it draws" rule, which had partylist and targetbar carrying separate copies of the same XivParty art and left the crossbar's 1,300-icon pack unreachable to anything else. Paths are addon-root relative (`assets/icons/...`), which is what `ctx.asset` already resolved - the per-component `ASSET_DIR` prefixes are gone. One directory may back **several lists of the same widget over different data** - `src/components/partylist/` draws the main party and both alliance parties from one factory, told apart internally by a variant. They were three separate registrations until 2026-08-30 and are now one component with three anchors; either way, three directories would force a cross-component `require`, which the rule below forbids outright, so one directory is the smaller deviation. It may require `lib/`, never a sibling component; cross-component needs go through the framework. The name is the shared key across code dir, config namespace, registry entry and command word, and is validated at registration (it cannot collide with a reserved `//hud` verb).
- **One read of the client per interval (`lib/player`).** Every component asks `ctx.get_player()` / `get_party()` / `get_info()` / `get_mob_by_target()` rather than reaching the client. **Three reads stay raw, on purpose**: core's own `get_player` and its `logged_in` (its login scoping retries both every 0.05s, which is the visible delay before the HUD comes up, so a 200ms cache would answer three of every four attempts from the same stale nil) and the crossbar's `chat_open` (asked on every key event to decide whether a key is the game's chat box or the bar's, where a verdict an interval old would swallow the first keystrokes after a chat line opens). Everything else, the crossbar's per-frame `zone` included, goes through the service. Two jobs. **Deduplication**: five callers wanted the player and four the party inside every 200ms, and `get_mob_by_target` ran about thirteen times a frame over six distinct signatures because the three party lists each ask for the same four; the player, party and info reads are now cached for 200ms and the mob lookups memoized for the frame (cleared by `begin_frame`, since a target can change between any two frames but never inside one). **Reconciliation**: FFXI reports vitals as two independent streams, and the components each reconciled them differently - parambar from the events alone, which is how an HP number could stick at max HP for a whole session; partylist by dropping its event values on every poll, which was right; targetbar by ignoring the events entirely. Now there is one policy in one file, for the vitals the client reports about **you**: **the client is the authority, and a change event carries the bars until the next read of the client overrules it.** The party list keeps a second, narrower overlay of its own (`live.own_vitals`, and the `0x0DD` / `0x0DF` pushes beside it) because its rows' numbers come from `get_party()`, which the service does not merge into - that is other people's vitals, and out of scope for a service about the player. A consumer that must tell a fresh read from a cached one calls `ctx.generation()` - partylist and targetbar gate a roster rebuild on it (rebuilding drops the packet pushes they hold) and the crossbar gates its recast reads on it. **Reading the counter opens the interval**, deliberately: a consumer may gate every one of its reads behind it, and if only a read could advance it that consumer would go quiet after its first frame, working only for as long as some other component happened to read the client earlier in the same frame. They gate on **that counter and never on a clock of their own**: a second throttle would sit out of phase with the service's and leave them up to two intervals behind, which is why `partylist`'s `poll_interval_ms` setting is gone (2026-08-30). An absent `ctx.generation` falls back to rebuilding every frame rather than never - Lua's nil-tolerance would otherwise turn a wiring slip into a frozen widget. There is deliberately **no subscription layer**: a missed `subscribe` would be a silently dead component, and Windower fails silently by design.
- **Widget contract.** `new(ctx) -> widget` exposing `name`, optional `alias` (its short name inside `//hud`, see Commands below), `defaults`, `attach(config, save, store)`, `detach()`, `set_pos(x, y, anchor)`, `set_scale(s, anchor)`, `set_preview(on)`, `show(anchor)`, `hide(anchor)`, `get_bounds(anchor) -> x, y, w, h`, `update(event, ...)` (no arguments is the per-frame tick), optional `handle_command(args) -> message` (a string, or a **list of strings** when one line will not do - an ordering or a search result; core says each), and `destroy()`. Four further members are opt-in, covered in the two bullets below: the `wants_store` flag, `anchors()`, `on_keyboard` and `on_mouse`. **A widget declaring none of them sees exactly the contract it always had** — `store` is nil, the trailing `anchor` argument is nil (`show`/`hide` included, since core only ever addresses an anchor a widget declared), and no input reaches it — which is why parambar, giltracker and the party list needed no edits when the crossbar landed. Core owns visibility and layout persistence; a component never decides whether it is on screen. **`get_bounds()` must return the same origin `set_pos` was given** — core clamps the widget on screen by comparing the two, and layout mode's drag offsets assume it; on a multi-anchor widget that holds per anchor.
- **Multi-anchor widgets.** A widget whose pieces are placed independently declares `anchors() -> {names}` and moves `pos`/`scale` under those names in its layout defaults (`layout.anchors.<name> = { pos = , scale = }`, no top-level `pos`). **`visible` is per widget AND per anchor** (added 2026-08-31), and the two are independent switches read in opposite directions: the widget's must be `true` exactly (a broken file must not switch a whole widget on), while an anchor's is **absent means shown** and only an explicit `false` hides one — so `layout.repair` fabricates none and a file that has never had an anchor switched off carries none (switching one back on writes `visible = true` rather than clearing the key - it is the answer to a command the user just gave), and a component that wants one off out of the box says so in its own layout defaults (`partylist`'s two alliance anchors do). The widget's flag outranks: switched off, the whole thing goes down whatever its anchors say, and hiding every anchor still reports the widget as shown. Core always states the widget itself first — the **bare** `show()` / `hide()`, which every widget hears whether or not it has anchors — and a bare `show()` means *the widget is on with every anchor on*, so a widget must let it undo every per-anchor hide: it is the whole of what layout mode force-shows with, and a hidden anchor that stayed hidden there could never be dragged or switched back on. It then restates each anchor as `show(name)` / `hide(name)`, rather than leaving the widget to infer the anchors it did not hear about. Core then pushes, clamps, describes (`//hud list` prints a headline plus one line per anchor, each with its own `shown`/`hidden`) and highlights one placement per anchor (a hidden anchor's box greys, exactly as a hidden widget's does), and layout mode hit-tests per anchor — a drag, a wheel-scale or a SHIFT + right-click addresses the anchor under the cursor, later anchors winning over earlier ones; a plain right-click still toggles the whole widget, and so does SHIFT + right-click on a widget that has no anchors to narrow to. Detection is **the member, never a convention**: absent `anchors()` (or when it answers a non-table), everything above takes the single-anchor path with the old signatures untouched — Lua's silent nil-tolerance makes an implicit rule too dangerous here. `layout.repair` keys off the *defaults* instead, and sheds a stray top-level `pos`/`scale` from an anchored entry as it repairs it. Two components are multi-anchor. `partylist` has three (`main`, `alliance1`, `alliance2` - the main party and the two alliance parties, which were three separately registered components until 2026-08-30), and `crossbar` has six (`main`, `wxhb_left`, `wxhb_right`, `set`, `weapon`, `skillchain_indicator` - the last three being the active-set label, the drawn-state sword and the skillchain bar. The first two were split off `main` on 2026-08-29 because riding it at a fixed offset meant the only way to move either was to move the whole bar; the third was `indicator` until the same day, a name that said which shape it was rather than what it was for.)
- **Component input.** `on_keyboard(key, down, flags, blocked)` and `on_mouse(mouse_type, x, y, delta)` are optional members; returning `true` propagates out to Windower as the block, and core ORs the answers together. The mouse signature carries no `blocked`: core answers an event a prior addon already took itself, so the flag would be false on every call a component could ever see - unlike the keyboard, which is forwarded whole precisely because core does *not* short-circuit there. Both handlers are registered for as long as *some* component declares one (`core.wants_keyboard()` / `wants_mouse()`), not just while layout mode is on, and `unload` releases them. **Layout mode owns the mouse outright** — while it is on no component sees a mouse event, and entering it exits a component's edit mode, so the two can never contend. Keyboard is the opposite by design (pinned 2026-08-16): core keeps **delivering** keyboard events during layout mode, under suppression and while logged out, so that a component *can* keep blocking its dedicated keys and tracking their state; the inertness belongs inside the component, not in dispatch going quiet — which would make blocking impossible. Delivery is all core promises: what a component does with an event is its own call, and a detached one (logged out, so nothing is attached) blocks nothing at all - the crossbar's keys go back to the game until a character is scoped. For that, core exposes `core.suppressed()` (the auto-hide resolver is hiding the HUD) and `core.component_visible(name)` (the user's own `visible` flag, what `//hud show|hide` and the right-click write, untouched by suppression). Both reach a widget as `hide()`, and only core can tell them apart: the crossbar ranks **disabled above suppressed** — suppressed means inert but still swallowing its five dedicated keys (handing `;` back to the chat box mid-cutscene would be worse), disabled means every key falls through to the game.
- **Tests (`tests/`).** busted specs `require` a module and pass fake deps. See `tests/core_spec.lua` and `tests/support/fakes.lua`. `tests/sources_spec.lua` is the exception: it `loadfile`s every file under `src/` so every file is at least known to compile, and checks the licence headers and the require convention. The entry point has a second exception of its own: `tests/entry_point_spec.lua` runs it, over `tests/support/entry_point.lua`, which `loadfile`s `src/XIVHud.lua` and hands it a fake `windower`, `io` and `require` through Lua 5.1's `setfenv` (`lib/core` and every component factory stubbed, `lib/guard` real). That covers the **wiring only** — what it registers, what each ctx is built from, and what the chunk dispatch pre-parses — because a decision made there is invisible to every component spec. It is not a licence to move logic into the entry point, and the harness header lists where each fake diverges from the client.
- **Require paths — use slashes, not dots.** Internal modules are required as `require('lib/core')` and `require('components/parambar/logic')`. Dot form *should* work (Lua's own loader rewrites `.` to the path separator), but the only addon in the Windower repository that requires across subdirectories — `bluguide` — uses slashes, and that is the form with evidence behind it. Both resolve under busted, because `.busted` sets `lpath` to include `src/` and `?` is substituted literally; at Windower runtime the addon's own folder is the require root, with `src/` as its stand-in here. `tests/sources_spec.lua` fails the build if dot form reappears.
- **A failed load must stay diagnosable.** If the main chunk dies part way, every `register_event` after the failure never runs: the addon answers no commands, writes no config, and cannot be investigated from inside the game — the worst possible failure, and one this repo has already hit. So `src/XIVHud.lua` loads in isolated steps that record why they failed, and registers the `addon command` handler **before** any of them; `//hud` then reports the failure. If loading fails, nothing else is registered and nothing is drawn.
- **Every Windower handler is wrapped** by `lib/guard`. `prerender` runs each frame, so an error there recurs sixty times a second and buries the one useful message; guard reports the first distinct error per handler, swallows repeats, and disables a handler after five failures. The mouse and keyboard handlers fall back to `false`, because a dead handler that keeps swallowing input is indistinguishable from a frozen client.

## Settings

Per-component isolation: every component owns its own configuration file and can never reach another's.

- **Storage:** every component owns the directory `data/<Character>/<slot>/<component>/`, relative to the addon root, holding two files core writes — `config.lua` (the component's own settings) and `layout.lua` (its placement, which core alone writes) — plus whatever else the component adds beside them. Framework options live in `data/<Character>/core.lua` (`snap`, `slot`, `hideCutscene`), **outside every slot**: it holds the active-slot pointer, which cannot live in the thing it names. The extra files are the **store**: a component setting `wants_store = true` is handed `store` as `attach`'s third argument, `load(name)` / `save(name, table)` over `<component>/<name>.lua`, same sandboxed read and serialized write as the two core files. A name must be a plain word (`^[%w_]+$`) — it becomes a path segment, so anything else is refused rather than composed — and `config`/`layout` are reserved, case-insensitively, because they are core's and sit in the same directory. Found files are cached until the config is re-read; a *missing* one is re-read from disk on every call, so callers load on their own events (an attach, a job change) and never per frame. `//hud reset <component>` empties that directory (non-recursively — it is flat by construction) **in the active slot only**, and every re-read drops the cache, so `//hud copy`'s reload cannot leave copied bindings stale in memory. Only `crossbar` uses the store (per-job bindings, `<MAIN>.lua` plus `SHARED.lua`).
- **Format: Lua, not XML.** Windower's `config` lib can only serialize XML and the bundled `json` lib has no encoder, so `lib/settings` owns persistence itself: files are read with `loadstring` in an **empty environment** behind a `pcall` (config files are code — a broken or hostile one degrades to defaults plus a warning), and written by `lib/serialize` with stable key order for clean diffs.
- **Defaults merge:** user values win; default keys the user has never seen are added; keys the defaults do not mention are preserved. A component's `defaults.layout` is split off at registration to seed `layout.lua`, and is kept out of what seeds `config.lua` — so a component never sees its own placement in the table it is handed.
- **Character scoping:** the character name is unknown until login, so components are attached on login and detached on logout, and nothing renders while logged out. Core scopes on the **name alone** — anything else a component needs from the client it waits for itself, because the client fills the player in field by field and no single field vouches for the rest (see `parambar` below). The `login` event is a one-shot that can fire before `get_player()` can name the player, so `on_prerender` keeps looking: every 0.05s while the client says we are logged in, every 1s at character select, re-armed by each login event. A login that cannot be resolved leaves the character already scoped alone — dropping one is the logout's job — and keeps the search running, so logging in as someone else without a logout event still switches.
- **Layout slots: a slot is a DIRECTORY, and it scopes everything.** `data/<Character>/<slot>/` holds one directory per component, so switching slots switches each component's settings as well as its placement — the crossbar's bindings included. That is deliberate (decided 2026-08-29) and is a change of meaning from the old scheme, where a slot scoped `pos`/`scale`/`visible` alone and behaviour was character-wide. A component's `layout.lua` is `{ pos = {x, y}, scale = 1, visible = true }`, or `{ anchors = { <name> = { pos = , scale = } }, visible = true }` for a multi-anchor widget - where an anchor also takes a `visible` of its own, written only when it is switched off (absent means shown; see Multi-anchor widgets above). The set of slots is read off the disk, and **existing is not the test**: a slot is a directory holding at least one component directory with a file in it. Both halves earn their keep - `os.remove` refuses a directory on Windows, so a deleted slot leaves its empty tree standing and `dir_exists` alone would go on offering it (and refuse to re-create it), while a directory of *loose* files is a pre-slot install's `data/<Character>/<component>/`, not an empty slot. `default` and the active slot always count, whether or not either exists yet, and `default` cannot be deleted. Slot names are matched case-insensitively (a directory made by hand can be capitalised any way) and created lowercase. The active slot name is in core's config, validated against `^[%w_]+$` on the way out of that file (it becomes a path segment, and `//hud copy` imports another character's core.lua) and every layout write persists immediately. `//hud slot create` copies the active slot's whole tree, having first written it to disk; `//hud slot delete` removes the directory; **a switch re-reads disk and re-attaches every component**, which on the crossbar rebuilds its state from the new slot's bindings. A component with no file in a slot falls back to its own defaults.
- **`//hud copy <source> <destination>`** replaces the destination's `data/<Character>/` tree — every slot in it — with the source's: the destination is emptied first, so what remains is the source's configuration and nothing else. Both ends are named explicitly, so it does not depend on who is logged in, and it reloads only when the destination is the character being played. It is destructive and has no undo and no confirmation step.

## Commands

`//hud` (alias `//xivhud`). Verbs and component names match case-insensitively; a component also answers to its short alias (`cb` wherever a component name is taken, as in `//hud cb list`); unknown input always answers with a hint, never silence.

```
//hud | //hud help              -- command list
//hud layout | setup           -- toggle layout mode
//hud list                     -- components with state, position and scale
//hud show|hide <component> [<anchor>]  -- a whole component, or one anchor of it
//hud reset <component|all>    -- restores defaults, in the active slot only
//hud slot <name>              -- switch layout slot (re-reads and re-attaches everything)
//hud slot list|create <name>|delete <name>
//hud copy <source> <destination> -- replace the destination's config with the source's
//hud <component> [...]        -- passthrough to the component's handle_command
```

Every component also answers to a short **alias** wherever its name is taken -
`//hud cb list`, `//hud show pb`, `//hud reset tb` - declared as an optional
`alias` beside the widget's `name` (2-4 letters or digits, starting with a
letter). The shipped set is `cb` crossbar, `pb` parambar, `gt` giltracker, `ev`
equipviewer, `tb` targetbar, `pl` partylist, `sc` speedcheck, `eb` expbar. The party list had none until
2026-08-30, and could not have had one: three registrations came off its single
factory, so a hardcoded alias would have had all three claim `pl` and the second
would have aborted the load. Collapsing them into one anchored component is what
freed the word. `//hud list` prints the alias beside the name, which is the only
place they are enumerated: help cannot name components it does not know.

It is a **parser** shorthand and nothing more. A bare `//cb` is not available
and was deliberately not built (decided 2026-08-30): the only mechanism for it
is Windower's own console alias (`windower.send_command("alias cb hud
crossbar")`), which claims a client-wide word the player and other addons share,
and `_addon.commands` cannot stand in - the `addon command` event is passed
"everything after the command, not the command itself", so an addon registered
under several names cannot tell which one was typed.

`lib/registry` validates the alias at registration, exactly as it validates the
name, and refuses a clash with a reserved verb, `all`, another alias, any
component name (its own included, in either direction) - a hard error at load,
where it is visible. `tests/component_aliases_spec.lua` registers every shipped
component together, since a per-component spec can only speak for its own.

Party list. One component over three lists, so every verb takes an optional
list word in front of it - `main` (the default), `alliance1` or `alliance2`:

```
//hud partylist                          -- all three lists and their settings
//hud partylist [<list>]                 -- that list alone
//hud partylist [<list>] spacing <px> | align top|bottom | emptyrows on|off
//hud partylist range num|icons | range <near> <far>
//hud partylist hidesolo on|off          -- main party only, as is range and every buff verb
//hud partylist buff                     -- the icon slots that actually get drawn
//hud partylist buff list [page] | find <text> | active [<member>]
//hud partylist buff top|up|down <id|name> | rank <id|name> <n> | reset
//hud partylist buff filter add|remove|clear|list [<id|name>] | filter mode blacklist|whitelist
```

The per-list on/off is **`//hud show|hide partylist <list>`** - the framework's
per-anchor `visible`, stored in `layout.lua`. It was `//hud show|hide
alliancelist1` while the three were separate components, then the component's
own `lists.<list>.enabled` verb (`//hud partylist alliance1 off`) for a day,
when `visible` was per widget and nothing in `//hud` addressed an anchor. Both
are gone: the framework switches an anchor now (2026-08-31), so a second
component-owned flag beside it could only disagree with it. **Nothing migrates**
- a stored `lists.<list>.enabled` is dead weight the settings merge preserves,
and a list switched on under either older scheme comes back on the shipped
default (main on, both alliance lists off, seeded as `visible = false` on those
two anchors in the layout defaults). `//hud show|hide partylist` and layout
mode's plain right-click still take all three lists at once; SHIFT + right-click
takes one.

Naming a list at `hidesolo`, `range` or any `buff` verb is REFUSED rather than
quietly applied to the main party or quietly stored where nothing reads it. All
three are structural: 0x076 carries the main party alone, an alliance row draws
no buff icons, and the alliance row layout has no range block at all - `range`
was accepted and inert on an alliance list from the day the three were separate
components until 2026-08-30, when it moved in beside the other two.

Every verb that *shows* buffs deliberately reaches past the icon cap: only the first
twelve are ever drawn, so a buff you cannot see is a buff you cannot promote.

Target bar:

```
//hud targetbar                  -- the range mode in force
//hud targetbar mode auto|default|magic|ninjutsu|gun|bow|xbow
```

`auto` follows the main job (casters get `magic`, NIN `ninjutsu`, COR `gun`).
RNG deliberately lands on `default` and is told to pick a weapon: nothing in the
client says which one is equipped.

Equip viewer:

```
//hud equipviewer                        -- both toggles as they stand
//hud equipviewer encumbrance on|off
//hud equipviewer ammocount on|off
```

Exp bar:

```
//hud expbar                             -- the bar's mode, its numbers and all three rates,
                                            plus what it read for the master levels
//hud expbar clear                       -- drop the rate history
```

`clear` rather than `reset`: `//hud reset expbar` is the framework's own verb
and restores defaults, and two words that differ only in position would be read
wrong.

Crossbar (the widget answers `set`, bare `cycle`, bare `open`, `edit` and the
built-in actions itself; `commands.lua` answers the rest):

```
//hud crossbar                           -- job, active set, and where each view points
//hud crossbar help
//hud crossbar set <1-8>
//hud crossbar cycle                     -- advance the rotation
//hud crossbar list [<set>]
//hud crossbar wxhb [on|off]
//hud crossbar retry [on|off]
//hud crossbar bind <address> <type> [<action>] [<target>] [alias=<name>] [icon=<name>]
//hud crossbar unbind <address>
//hud crossbar alias <address> [<name>]
//hud crossbar icon <address> [<name>]
//hud crossbar swap <address> <address>
//hud crossbar view <wxhb-L|wxhb-R|exp-LR|exp-RL> <set><L|R>
//hud crossbar share <set> on|off
//hud crossbar cycle <set> drawn|sheathed|both|none
//hud crossbar copy <JOB>
//hud crossbar context list
//hud crossbar open [<name>]
//hud crossbar draw
//hud crossbar mr
//hud crossbar sneak
//hud crossbar invisible
//hud crossbar warp [all]
//hud crossbar edit
```

An **address** is one word, `<set><L|R><slot>` - `1L1`, `2R8` - and takes the
layer prefixes `sub:` and `ctx:<name>:` in front on the four verbs that write
one layer. It was three words (`1 l 1`) until 2026-08-22: a lower-case `l`
beside digits is indistinguishable from a `1` in the game's font, so the side
is written upper case (either case parses) and the three words are one, which
cannot be miscounted either. The slots' controller names went at the same time
- there is no controller for them to name - so a slot is 1-8 and nothing
else.
Two verbs are deliberately overloaded: bare `cycle` advances the rotation while
`cycle <set> <mode>` edits membership, and bare `open` lists the screens while
`open <name>` opens one.

`bind`'s trailing alias and icon - the same two overrides the `alias` and
`icon` verbs write afterwards - are each opened by a MARKER, `alias=` and
`icon=`, matched in any case and in either order. They were positional and
QUOTE-delimited until 2026-08-30, when a live client settled testplan row C26:
Windower groups a quoted run into ONE argument and strips the quote characters
before the addon is asked, so the grammar's own test (`word:sub(1, 1) == '"'`)
could never be true in a client and every label was silently swallowed by the
action name. The marker is what survives that trip, and it also ends the
action name - the one job the quotes used to do, which is why a ONE-WORD name
can carry a label now (`ma Cure alias=C`): `"C"` and `C` reach the addon as
the same word, so nothing else could have told them apart. A value runs to the
next marker or the end of the line, so `alias=Big Hit` needs no quotes of its
own and all three shapes `alias="My Alias"` can arrive in - one argument, two
with the quotes still on, two bare words - read as the same alias. An empty
value (`alias=`) is no label at all. Every type takes them, a `ct` or `ex`
line included: the marker is the only thing that can end a line, so the line
keeps every word up to it, and a line needing a literal `alias=` in it must be
quoted as a WHOLE (`ct "p alias=x"` arrives as one argument, which the marker
pattern never matches, and stores `p alias=x`) - unquoted, that line binds `/p`
under the label `x`. A `ct`/`ex` line also gets the user's own QUOTING PUT BACK, without
which `ct ma "Cure IV" <t>` would say `/ma Cure IV <t>` and never cast: an
argument can only carry whitespace where the user quoted it (the client groups
a quoted run and strips the quotes), so a word with a space in it is one they
delimited and is re-quoted before the words are joined. A word already
carrying a quote is left alone - it came from a client that hands quotes
through, which never produces a word with whitespace in it, so the two
readings never meet. Quoting around a SINGLE word is the one thing that cannot
survive, being indistinguishable from a bare word on arrival, and the game
reads `/ma Cure <t>` the same way regardless. The cost, and it is a real one: a
quoted phrase in a CHAT line is now said with its quotes (`ct p "Hello there"`
says `/p "Hello there"`, where the old joining said it plainly) - the two
cannot be told apart, and a spell name that will not cast is the worse of the
two failures. Chat text is written unquoted. Quotes around the WHOLE line come
off again (`ct "sea all linkshell"`), that pair being the line's own wrapper
rather than a phrase inside it. Both of these and the loss of a literal
`alias=` inside a line are consequences of the marker grammar, not decisions
taken separately - they are Kevin's to overturn, and doing so means giving up
`ct ma "Cure IV" <t>`. A TARGET still goes in front of the labels;
one arriving after them as a word of its own is refused rather than swallowed,
since an aim that vanished into an alias would bind an action pointed at
nothing - but only on the types that could have TAKEN a target (the game types
and `ra`), and only where the client split it off as its own word. On `warp`,
`ct` or `open` a target token is an ordinary word of the alias (`Follow me`),
and refusing it would leave the user nowhere to go: `warp` and `open` refuse a
bare `me` in front of the labels too, so it could not be moved there, and on a
`ct` line moving it in front is a silently DIFFERENT bind - the word is part
of what gets said. A value the client
handed over whole (`alias="Cure p1"`) is one the user delimited and is left
alone either way, which is the way out the refusal itself spells. A quote left
in a GAME action's name is refused for the same reason a bad icon is - nothing
is called `"Cure IV`, so it could only ever have been a bind that never
fires - while a `ct`/`ex` line keeps every quote it was given. An icon naming art that does not resolve
refuses the whole bind - a bind is one command, and binding the action while
dropping the art silently would be worse. `//hud crossbar list` prints each
label marked and quoted (`alias="Cure 4" icon="cure"`), so a listed row
retyped binds the same thing whichever way the client splits it - bar a value
carrying a quote OF ITS OWN, which nothing can quote back and which only a
quote-passing client could have stored in the first place.

Quotes now do exactly one thing in the parser: a value that arrives wrapped in
a MATCHED pair is unwrapped and trimmed (commands.lua's file-local
`undelimit`), which is what a client that hands the quotes through would
produce. The pair is matched by checking the inside for a quote of its own -
`"/p a" "b"` opens and closes with one without those two being a pair, and
stripping them would delete characters out of the middle of what was typed, so
it is left alone (as is a delimited line that really does carry interior
quotes: storing what was typed beats silently editing it). A lone quote is a
character in the name - a chat line carrying one is a line someone means to
say, and refusing it would refuse what nobody can otherwise type - except in a
GAME action's name, where it is refused, above.

In layout mode: left-drag moves a widget (snapped to the grid; hold CTRL for free movement), the wheel scales it (floor 0.25), right-click toggles it on or off. A multi-anchor widget drags and scales one anchor at a time — the one under the cursor — and **SHIFT + right-click toggles that one anchor**, while a plain right-click still toggles the whole widget. SHIFT is tracked through the same keyboard handler CTRL is, so the caveat there applies to it too. Every change persists immediately. Auto-hide outranks layout mode: the HUD stays hidden during a cutscene (player status 4, disable with `hideCutscene`), while zoning (plus a ~3s settle), and while logged out.

## Components

- **`partylist`** (`src/components/partylist/`) — the FFXIV party list: the main party and both alliance parties, each independently positioned, re-implemented from [XIVParty](https://github.com/Tylas11/XivParty) 2.2.0. **One component over three lists**, placed through three anchors (`main`, `alliance1`, `alliance2`); a variant per list picks the party keys (`p0..p5` / `a10..a15` / `a20..a25`) and which of the two row layouts to draw. It was three registered components (`partylist` / `alliancelist1` / `alliancelist2`) until 2026-08-30, one config file and one layout slot apiece. The merge is what freed the `pl` alias, and it moves three things: the per-list on/off is the framework's PER-ANCHOR `visible` (`//hud show|hide partylist alliance1`, and SHIFT + right-click in layout mode) - briefly the component's own `lists.<list>.enabled` while `visible` was per widget, replaced on 2026-08-31 by the framework switch rather than kept as a second flag beside it, every command takes an optional list word in front of the verb, and the three config files become one - **nothing migrates, by decision**, and that is wider than the placements: the old `config.lua` keys were top-level (`item_spacing`, `align_bottom`, `show_empty_rows`, `range`, `hide_solo`, and `buffs` - the hand-curated priority order and filter list, the most laborious setting the component has) and are read from `lists.<list>.*` now, so a stored file comes up on fresh defaults with its old keys left in it as dead weight (the settings merge preserves what the defaults do not mention). An alliance list switched on under either older scheme comes back off too - the shipped default is `visible = false` on both alliance anchors in the layout defaults, absent (so shown) on `main`. `partylist.lua` is an inner factory per list under an outer widget that routes the contract by anchor, so the three keep their own logic instances, prims and boxes, and each hears its own `show`/`hide`; a list that is off is still force-shown in layout mode by the widget's bare `show()`, or it could never be dragged back into place. `logic.lua` is the pure state machine (roster, bars, colour bands, distance dimming, buff ordering, the command parser, the layout-mode preview); `packets.lua` parses `0x0C8` / `0x0DD` / `0x0DF` / `0x076`; `layout.lua` is the hardcoded `xiv` geometry; `buff_order.lua` and `jobs.lua` are ported data. `partylist.lua` owns the prims and builds a row's set only when that row is occupied. Buff settings belong to the **main list** alone (`lists.main`) — `0x076` carries the main party only, and the alliance row has no buff icons; `hidesolo` and `range` are main-only for the same kind of reason. `src/assets/xiv/` holds XIVParty's `xiv` art, its `jobIcons/` and `buffIcons/` beside it, redistributed under the BSD 3-clause notice in `assets/xiv/LICENSE.txt` (© 2024 Tylas).
- **`parambar`** (`src/components/parambar/`) — the FFXIV parameter bar: HP/MP/TP fills with numbers, re-implemented from XIVBar. `logic.lua` is the pure state machine (easing, colour bands, layout maths, its command parser); `parambar.lua` owns the prims. `src/assets/ffxiv/` holds XIVBar's theme art, redistributed under the BSD 3-clause notice in `assets/ffxiv/LICENSE.txt` (© 2017 SirEdeonX) — that file ships with the addon. Commands: `//hud parambar [width|spacing|offset <px> | compact on|off]`. **It holds no vitals of its own.** `ctx.get_player().vitals` is read every frame and pushed straight into the state machine, already reconciled by `lib/player` - the widget hears no `hp change` event and owns no interval. That is a fix as much as a refactor: parambar used to take the absolute stream from the events alone, and after a Max HP Down (curse) wore off the HP *number* sat at max HP for the rest of the session while the bar and its colour band tracked the real percent (reported around equipment changes too) - XIVBar's unreconciled-streams defect, on a trigger the 0%-means-dead rule does not cover. **Why the event stream carried max HP at all is unverified** and needs a live client. Only bars whose numbers actually moved are marked dirty, so reading every frame still costs nothing once settled; a vital the client has not filled in yet reads 0 for a frame or two after login rather than until the player next casts.
- **`targetbar`** (`src/components/targetbar/`) — the current target's health bar: a `HP% | distance | name` row above a bar drawn on the same XIVParty `xiv` art the party list uses, re-implemented from the Windower `enemybar` addon with [DistancePlus](https://github.com/Windower/Lua/tree/dev/addons/DistancePlus)' range colouring. `logic.lua` is the pure state machine (ease, claim state, hp bands, range bands, the command parser, layout maths); `targetbar.lua` owns the prims. `assets/xiv/wide/` holds partylist's three bar textures **regenerated at two widths** (4x for the health bar, 2x for the cast bar) under its own `LICENSE.txt` (© 2024 Tylas) — beside the originals in `assets/xiv/` rather than in a directory of its own, since they are the same art at another size. They cannot be deduplicated: same names, different pixels. **Three colour channels, deliberately independent**: the hp number bands (partylist's `< 25 / < 50 / < 75`), the distance follows DistancePlus' job-aware bands, and the **bar fill carries enemybar's six-state claim palette** — moved off the text, where the reference put them, onto the fill, with one colour changed: claimed-by-us is deepened to `255,20,20`, because the reference's pale pink was picked for text and washes out across a fill. Two fixes over the reference's `check_claim`: the ownership set is the whole **alliance** (it only scanned `p1`–`p5`), and an **unclaimed mob is never "mine"** — the reference initialises its player id to `0` and compares it to `claim_id`, so before the player resolves it paints every free mob as claimed by you. The claim roster and the player ride `lib/player`'s read counter rather than a clock of their own; the target itself is read every frame, and memoized there so the party list asking for the same one costs nothing. **The bar frame draws at 512x64, from art regenerated for that width** — never by stretching the texture at runtime, which would warp the bevelled caps. The source art's middle is a run of identical columns, so the wide version preserves both caps byte for byte and extends the middle by replicating the centre column: no pixel is interpolated (the same move as partylist's regenerated row panel; transform documented in `assets/xiv/wide/LICENSE.txt`). Only the fill inside the frame is stretched at runtime, to the health percentage. The framework's uniform scale is the only way to resize the widget, and all vertical placement is measured from the visible band at drawn y 25..39 (texture rows 50..77 at 2x) rather than the art's own top, which is 25px of transparent padding that would otherwise draw above the origin. **The cast bar**: a smaller second bar (its own half-width art drawn at 0.67, about a third of the health bar), right-aligned under the first with the spell or TP-move name beneath it, raised while the target winds something up. It rides the existing `incoming chunk` dispatch - the `0x028` action packet, which reaches the widget already decoded by **`windower.packets.parse_action`** in the entry point (core API, used the same way by GearSwap/Debuffed/enemybar2; the `action` *event* is deprecated and deliberately not used), since the crossbar's skillchain engine reads the same packet and one decode serves both. Spell fills run against `res.spells[].cast_time` (seconds); TP moves have no duration in any packet or resource, so theirs is a fixed `tp_move_sweep` animation. Interrupts are structural - a start-shaped packet whose one action has `message == 0` aimed back at the caster - and every bar carries a duration+grace expiry besides, so a finish the stream never delivers still clears. Without the resources library the cast feature alone sits out (no names to show); the rest of the widget carries on.
- **`equipviewer`** (`src/components/equipviewer/`) - the equipped gear grid: sixteen item icons in the reference's 4x4 arrangement, an X over any slot encumbrance has locked, and the ammo count over the ammo icon, re-implemented from the Windower `equipviewer` addon (© 2021 Tako/Rubenator). `logic.lua` is the pure state machine (what is in each slot, the encumbrance decode, the ammo count, layout maths, its command parser); the pure half of the icon extraction lives in `lib/icons` and the queue-and-cache discipline around it in `lib/icon_cache`, promoted out of this component so the crossbar can draw item art without requiring a sibling (CLAUDE.md forbids that outright, and duplicating the byte-level DAT parsing is exactly what the isolation rule exists to prevent); the Rubenator notice travels with the code. `equipviewer.lua` owns the prims and the io. **No icons ship with the addon** - there are tens of thousands of items and the art is the game's, so the first time an item is seen its icon is read out of the client's own `ROM/*.DAT` files, decoded and cached as a bitmap under `icons/` beside the addon (shared across characters, gitignored and stripped from the package). It is deliberately **not** under `data/`: `//hud copy` enumerates every directory there as a character, so a cache alongside them would be offered as one and `//hud copy icons <character>` would wipe that character's configuration. The record is a 256-colour palette plus one index byte per pixel, every byte of it bit-rotated (`(i % 32) * 8 + floor(i / 32)`) with alpha stored at half scale; `icons.to_bmp` un-rotates the palette only - 256 entries, not 1024 pixels - and expands the pixels through it in one `gsub`. Two oddities of the reference's header are kept deliberately: the colour space is written as the literal `sRGB` (the LCS_sRGB constant byte-reversed) and the height is positive, so rows read bottom-up. **Extraction is queued, one icon per frame**, never done where the packet arrives: a first login with nothing cached would otherwise mean sixteen DAT opens, decodes and file writes inside a single frame. An item that fails is abandoned for the session rather than retried every frame — behaviour that now lives in `lib/icon_cache` and is shared with the crossbar, one `<addon>/icons/` directory between them, so an item either component has extracted is never extracted again. The game path is `windower.ffxi_path` (undocumented - the wiki has `pol_path`), falling back to `pol_path`, with a `game_path` setting overriding both. The write goes through the entry point's `write_binary`, which opens `"wb"`: the existing `write_file` uses text mode, and on Windows that would turn every `0x0A` byte of a bitmap into `0x0D 0x0A`. Encumbrance is decoded with arithmetic rather than LuaJIT's `bit`, which is not part of Lua 5.1 and could not be tested here. Deviations from the reference: position, scale and visibility are framework-owned (its `pos`/`size`/`scale`/`justify` verbs are gone), so are `hide_on_zone` and `hide_on_cutscene`; the ammo count is left-justified for the same reason giltracker's number is; the equipment table is read once per refresh rather than once per slot; a job change is caught on `0x01B` rather than by registering an outgoing chunk handler that would see every packet the client sends. `assets/encumbrance/encumbrance.png` is redistributed under the BSD 3-clause notice beside it (© 2021 Rubenator, base extraction code credited to Trv); `assets/own/panel.png` is XIVHud's own white square, tinted for the panel behind the grid.

- **`speedcheck`** (`src/components/speedcheck/`) - the player's movement speed as a signed percentage, drawn under Bolter's Roll's status icon, re-implemented from the Windower `SpeedChecker` addon (BSD (c) 2013-2014 Windower). `logic.lua` is the pure state machine (the percentage, the centring and the layout maths); `speedcheck.lua` owns the prims. The reference is one prerender handler and one text: `movement_speed` off `get_mob_by_target('me')`, whose walking value is 5, so 5.6 reads +12%. The field is on the **mob** table and not the player one, and no packet carries it, so it has to be polled - on `lib/player`'s read counter rather than on the frame, since the mob memo is cleared every frame and a read per frame would be a real client call sixty times a second for a number that moves when a buff, a mount or a piece of gear does. Nothing is read while the widget is off screen either, and the prim is written only when the number it would draw has actually changed. Asking for the counter is what opens the next interval, so the widget keeps its own cadence even when no other component reads the client. The art is XivParty's `assets/xiv/buffIcons/330.png`, the Bolter's Roll status icon (a running figure over a speed arrow - the one icon in the game that says what this widget is), so nothing new ships and no new notice is needed. A character switch with no logout event behind it does not detach at all - core re-attaches over it - but the attach reads immediately, and the player service has already been invalidated by then (core announces the scope change before attaching), so nothing stale is drawn. The two are STACKED, icon over number (the number was drawn ON the art until 2026-09-04, when a live client said otherwise), and the number is centred on the width of the string actually drawn rather than left-justified the way giltracker's is - a prim cannot be right-justified without being offset by the screen width. The BOX is measured against the widest string it ever draws (`-100%`) instead, which is what keeps the icon and the origin still while the value moves; the box is as tall as icon, `text_gap` and number together. `get_bounds` hands back that box, at the origin `set_pos` was given, as the contract requires. Text width cannot be measured from a prim, so the centring is estimated from the font size and `text_offset` is the knob for correcting it in a live client - it moves the number against the icon, and the box grows to cover wherever that puts it (a negative correction pads the box's left instead, shifting both prims across), so the correction can never put anything outside what core clamps and layout mode highlights. **Whether `movement_speed` reports a capability or a current velocity is unverified** and needs a live client; the reference's own design - a static percentage read every frame - assumes the former. No commands.
- **`expbar`** (`src/components/expbar/`) - the FFXIV experience bar: one filling bar with a status line above it, re-implemented from the Windower `pointwatch` addon with `barfiller`'s art and none of pointwatch's Abyssea, Dynamis, sparks, accolades or unity readouts. `logic.lua` is the pure state machine (mode selection, the packet and message reads, the rate registries, the header text, the ease and layout maths, its command); `expbar.lua` owns the prims and every ctx read. The main job's glyph is drawn from XivParty's `assets/xiv/jobIcons/<job>.png`, standing left of a header and bar that share a left edge and SPANNING both of their rows - square, and as tall as the two together, so it is derived from them rather than written down beside them (the widget's origin is the icon's, so nothing draws left of what core clamps) - **bare** - it is gold with a dark outline, so it needs none of the tinted backing the party list puts under the same art for its role colours, and drawing it needs no job data at all. Glyph, header text and bar fill are ONE gold (Kevin, 2026-09-04): the crossbar's `255,215,0` for the text, and barfiller's fill art, which is already a gold gradient - so the fill ships tinted white, which modulates that art to itself, and the three bar modes are told apart by the line above the bar rather than by a tint the gold art could not carry. The header band is as tall as the taller of the text and the glyph, so an icon sized past it pushes the bar down instead of drawing over it. **The bar's width is derived, not barfiller's fixed 472**: it runs from the header's own left edge to an overhang past the longest line that header can ever print, which `measure.lua` sums from the widest header at `font_size * text_width_ratio` per character (286 at the shipped 8pt, in a widget the icon makes 305 wide). `text_height_ratio` is the same shape of estimate for the height, and places the bar under the header as well as sizing the icon. Both were settled against a live client, which is also where 8pt came from - 11 drew far too large - and where the icon's own uneven art padding showed up: of its 64px square WHM's glyph starts 18px in and WAR's 4px, so the apparent gap before the text varies by job and `job_icon.gap` is kept to 1. Windower cannot be asked how wide a string will draw, so that ratio is an estimate and is config for a live client to settle; the sample it measures is pinned against the real header driven to its longest, so the format cannot outgrow the bar unnoticed. The 472 art is squeezed to whatever comes out, costing a fraction of a pixel off each 2px cap. `assets/barfiller/` holds the 472x5 frame and the 1px fill, redistributed under the BSD 3-clause notice beside them (© 2015 Morath86); the component's own `LICENSE.txt` covers what was transcribed into its Lua (© 2014 Byrthnoth for pointwatch, © 2015 Morath86 for barfiller). **THREE bar modes, not two** (Kevin, 2026-09-04): below the level cap the bar fills with experience toward the next level; at the cap without the `Master Breaker` key item it fills with limit points toward the next merit, which is what the game's own bar does there and what a two-mode design would have left flat and empty; at the cap with it, exemplar points toward the next master level. The mode is read off `get_player().main_job_level` rather than 0x061's own level field, so a job change moves the bar without waiting for a packet, and the header's rate always names whatever the bar is filling with - EXP/hr, CP/hr or EP/hr - so a sub-99 character is not shown a capacity rate stuck at zero. **The client answers almost none of this**: `get_player()` carries no experience and no master level, so everything but the job pair and the job points arrives as packets (0x061, 0x063 order 2, and 0x02D for every gain in between), and the component **seeds itself from `windower.packets.last_incoming`** at attach - it is attached on login and on every slot switch, and nothing re-sends either state packet on request. That seed is reliable for 0x061 and **usually misses for 0x063**, which is multiplexed over five orders while `last_incoming` is keyed by id alone: only order 2 carries limit points and merits, and it is rarely the last 0x063 sent. That packet comes when limit points MOVE and in the bursts sent for a zone or the status menu, never on request - so a merit-capped character earning none reads **0 merits** until they zone or open the status menu (confirmed in a live client 2026-09-04). pointwatch behaves the same way and it is deliberately not worked around. So the numbers are held rather than re-read, and cleared only when the CHARACTER changes - the name read at attach, not the attach itself, since `//hud slot` and `//hud reset expbar` re-attach the same player and clearing there would put a zero on screen that nothing could fill back in. For the same reason a merit cap of zero reads as *not yet known* rather than as a cap: treating it as one parks the bar at 9999/10000 until the first order-2 packet arrives. Defects of the references deliberately not reproduced: messages 105 and 735 carry their amount in Param 2 (`${number2}` in the action-messages resource) and both addons read Param 1, so pointwatch's capacity rate counts chain numbers rather than points; pointwatch has no entry for message 253 at all, which is the experience chain and so most of what a party earns; and its exemplar branch registers a gain for the rate and then never adds it, so its EP figure moves only when a 0x061 arrives. Message ids 809/810 (exemplar) are past the end of the action-messages resource and rest on pointwatch alone - unverified, like the `Master Breaker` read, whether `Master Level` follows level sync, and whether a 0x02D gain message ever arrives about somebody else - nothing compares its `Actor` to the player, exactly as both references do, because a filter that guesses wrong kills the component silently while the absence of one merely over-counts.
- **`crossbar`** (`src/components/crossbar/`) - the FFXIV Cross Hotbar: sixteen slots drawn as two four-button crosses, raised by holding a side key, over eight sets and three bars (the XHB, the WXHB's two halves, and Expanded Hold on both side keys at once), re-implemented from the Windower `xivcrossbar` addon (MIT (c) 2020 AliekberFFXI; per-file BSD (c) 2017 SirEdeonX, inherited from `xivhotbar`). By far the largest component, and the only one that uses all three framework touchpoints it drove: four **anchors** (`main`, the WXHB's two independently placed halves, and the skillchain `indicator`), `wants_store` for per-job bindings (`<MAIN>.lua` in its own directory, plus `SHARED.lua` for the sets flagged shared), and both `on_keyboard` and `on_mouse`. `input.lua` is the pure DIK state machine (hold states, the switch chord, the block verdict); `bindings.lua` the layer stack (buff contexts over subjob overrides over the job base or the shared store); `render.lua` the geometry and the draw plan; `commands.lua` the authoring CLI - whose help gives every command its own line, a spaced ` | ` between two of them - and a pipe inside the verb itself, `alias|icon` - having read as one command with alternatives, so an argument's own alternatives are the only pipes left, `binder.lua` the mouse binder over `catalog.lua`; `actions.lua`, `stealth.lua` - the one-button `sneak` and `invisible` ladders, each walking a FIXED order (ninjutsu, then Spectral Jig, then the spell, then Silent Oil / Prism Powder) rather than preferring what the main job offers, so the same press behaves the same on every job and the item is only ever reached last; every rung is gated on what the CLIENT says - `get_spells`/`get_abilities` for what is known and the resource's own `levels` against the live main/sub pair, the same two questions `catalog.lua` asks of every other action, which is why a subjob change needs no notification - and a ninjutsu rung additionally wants its tool in the bag (`counters.tool_display`, master tools included on a NIN main exactly as a bound slot counts them), since the press would otherwise be spent on the game's refusal. The bag is read at the PRESS rather than off the per-frame `item_counts` tally, which is maintained only for ids some painted slot is bound to. An unreadable bag or an unresolvable item answers nil rather than 0, and a nil sends the press anyway: the game's own "you do not have that item" beats refusing a press that might have worked. Where it lands comes from the resource's `targets` bitfield - both ninjutsu and the jig are self-only and can never carry `<t>` - `openers.lua` - whose two chorded entries (the equipment and inventory windows, which have no slash command) inject their keys as ONE chained console command around a `wait`, the four edges sent back to back inside a single frame having never been sampled by the client at all - `roulette.lua` - which also answers a mount slot's AVAILABILITY, both halves of it being things the client will not answer for: the zone rule reads the zones resource's own `can_mount` (present-or-absent, never false, so the test is presence and an unresolved zone answers "not blocked" - dimming on ignorance would read as unusable at every login, the cost corner's rule), and the 60-second recast is tracked in the module because NOTHING names it, `get_ability_recasts()` being keyed by recast id and the job_abilities resource carrying no mount ability at all. The clock starts when the summon is SENT (Kevin's call, knowing a summon the game refuses leaves the slot dimmed for the minute anyway), on the MONOTONIC frame clock rather than the wall clock the extdata maths use. A press the addon knows will fail is refused in `actions.resolve` and is a complete no-op - no travel countdown, no command, no stamp - so nothing downstream needs cancelling. BOTH conditions refuse, not just the zone: the recast used to only DRAW, so a press mid-sweep still counted five seconds down and sent a summon the game was always going to turn down. The dim and the dead press are one rule, deliberately, having disagreed three times in a live client. The two conditions then part company once MOUNTED: the zone stops applying (the press is a dismount, which is never held up, and you can be riding where you could not have mounted) while the recast keeps counting and keeps the slot dim, being the one thing still true up there - skipping it alongside the zone made the sweep vanish the instant the mount landed - `warp.lua`, `enchanted.lua`, `enchanteditem.lua`, `counters.lua` and `skillchain.lua` the bindable behaviour - `enchanteditem` is the `enchanteditem` bind type, warp's ladder with the ladder taken out: one named piece of gear searched for across every equippable bag (`enchanted.candidates`, which answers EVERY copy ranked - reachable first, then the one on your hand, then bag order - so a spent ring on your finger cannot hide a charged spare in your bag; `enchanted.collect` is the one-winner form beside it, which the warp ladder uses and which deliberately has no worn preference for that same reason), resolved into the same three plan shapes so **one** scheduler in the widget runs either and the two cannot drift. That scheduler CHECKS THE PIECE ACTUALLY WENT ON before reading anything off it, and puts it back when it has not: `gs disable` stops future GearSwap swaps but cannot cancel one already in flight, so a set equipped in the same breath as the press lands on top of ours and the ring never reaches a finger - after which the extdata being polled belongs to a ring in the bag, and the use branch would fire `/item` at something not worn (refused by the game, and broadcast on by `warp all` regardless). It re-issues once a poll until the deadline rather than giving up early, since a GearSwap burst can outlast several seconds. It takes **no** travel countdown - the warmup already is the wait - and only one wait of any kind is ever in flight, so a pending warp blocks an enchanted item and the reverse. A deferred use **resolves its target at the press**, the way the cast retry does: the command goes when the enchantment comes up, so a `<t>` carried that far would land on whatever had been tabbed to since. A token the press cannot resolve - `<st>`, or `<t>` with nothing selected - is refused before any GearSwap slot is held, rather than deferred and resolved late. A slot bound to either `item` or `enchanteditem` also carries a **count** in its corner (`counters.item_display`: what the bag holds, capped at `99+`, drawn in plain white - no master-tool substitution and no colour bands, both of which are ninja-tool facts rather than item ones). Zero raises the red X and dims the slot **only where the zero is trustworthy**: gear always, a plain item only once a bag whose name contains `temporary` has been found, since a name miss there would otherwise cross out a press that works - a missing warning being the better failure. The bag re-read that feeds it is gated on the ids some painted slot is actually bound to, so an unrelated item moving costs nothing, and a **repaint** re-derives the set of bound ids and marks it dirty only when that set actually CHANGED - but `add item`/`remove item` fire only when a record ENTERS OR LEAVES a bag, so a decrement within a stack (four of five left) reached the count only when it emptied; the decrement rides the `0x01E` Modify Inventory packet instead, which the component already receives and which carries no item id, so it is gated on whether any painted slot draws a bag-fed number at all and coalesced by the same dirty flag - a bind or a context flip usually does, a hold state or a same-contents set switch does not, and marking every repaint dirty would re-read up to ten bags for nothing. Where it counts from differs by type and deliberately so: a consumable from the **inventory and the Temporary bag** (a potion in a wardrobe is not one the game will let you drink, but an item held temporarily is one `/item` can use - the bag is found by name, never by a remembered id, and read only when something is bound to an item id). Note the ladder does not share that scope - `enchanted.collect` walks equippable bags only - which is harmless for its own rungs, Instant Warp being an ordinary inventory item (confirmed 2026-08-21). Gear counts from every equippable bag; `retry.lua` the cast retry, which re-sends ONE refused action - a spell, job ability or weaponskill, each keyed to its own refusal message and its own blocking buffs (silence/mute stop spells, amnesia stops the other two) - reactive, never predictive (it reads the refusal off the `0x29` the component already receives, so a press the game accepted is never delayed), it **never holds an action blocked by a recast** (the defect that made the reference addon's queue unusable), and it **pins the target at the press** and re-sends the mob id in place of `<t>`, so a retry cannot wander onto whatever you have since tabbed to; `travel.lua` the travel delay, which holds `mount`, `mr` and `warp` for a configurable `delay` (5s, zero to switch it off) and counts it out in chat - the opening line names the RUNG (`Warp Ring in 5 seconds`, not a bare `Warp`: the ladder has several and the player is about to spend one) and only the last five seconds are spoken, since a warm-up's thirty would be a wall of text. A ring **warm-up** is narrated too, by the poll that owns its clock rather than a second one armed beside it: which item at the press, its length once the extdata can be read, then the last five - and resting calls it off like any other trip, releasing the GearSwap hold, which it never used to. The ladder is walked ONCE, so the rung announced is the rung that fires: resting cancels it - the trigger is the player STATUS, resolved from `res.statuses` by english name rather than hardcoded, so an unconfirmed fallback constant is only reached without the resources library - and so do the transitions that end any other moment (zone, death, logout, job change, suppression). Getting OUT of something is never held: mount roulette's dismount, a NAMED mount slot pressed while mounted (which dismounts rather than sending its summon - the two used to disagree, so the same press was instant on one slot and a five-second countdown on the next) and `draw` stay instant, and a warp skips the countdown when the rung it picks must be **equipped and warmed up** first - that wait already is the window, and the condition is the wait rather than the item, so an already-equipped charged ring counts down like a spell. `warp all`'s IPC broadcast rides the moment the LOCAL warp commits - the send for a spell or a charged item, the deferred use for a ring being warmed up, at once when the ladder found nothing - so neither a cancelled countdown nor an abandoned warm-up leaves the alts already sent home. **Opening a config mode ends a trip too**: `//hud layout` and the binder cancel one that is counting down and refuse one pressed while they are open (a late action fires only where a fresh press would - CB9's rule; an open chat line is deliberately not one of these, unlike the retry), and a re-attach - `//hud reset crossbar`, a `//hud slot` switch, and the reload after `//hud copy` - drops one too, since the configuration that armed it has just been replaced: the COUNTDOWN goes silently, a warm-up says `warp dropped - <item>` and releases its GearSwap hold, because a ring left on your finger with nothing coming is not something to work out from silence. A job change, a death, a zone and an opened config mode all end both halves - the last of those BEFORE the poll that would otherwise fire the very trip being called off. `crossbar.lua` owns the prims, the io and every `ctx` read. **There is no gamepad** — Windower cannot see one, so the bar reads keys and a Steam Input layout presses them for the player — and for the same reason **no modifier is used**: `return true` swallows a bare key completely but does not stop FFXI acting on a Ctrl/Alt chord (verified in-client, after two input designs died on that fact), and the game's own macro palette lives on exactly those chords. The five punctuation keys (`;` `'` `\` `` ` `` `=`) are the component's outright; the number row is the game's except while a hold state or the switch is up. **Weapon state is the component's own state machine**, never the client's status: `draw` toggles it, engaging in game also enters drawn, and a mob dying does not leave it - so the cycle rotation cannot lurch back mid-pull. Entering a state LANDS the bar on the first set of that state - the lowest-numbered non-empty one flagged for it - and so does loading a job, which sheathes you without a transition and so reconciled nothing: on a config whose low sets are drawn-only, a job change landed on a set the sheathed rotation does not contain. The landing is the same every time, which is what makes a combat set worth arranging, and it means the stored per-job `active_set` no longer decides where a job resumes (Kevin's call, made knowing that). A state with no non-empty set flagged for it leaves the active set alone - stranding the bar on nothing would be worse. **Entering a state also moves the active set** to the FIRST set of that rotation - the lowest-numbered non-empty one flagged for it, a jump rather than an advance, so drawing always lands you on the same combat set whatever you were on. Only a real transition does it: `on_status` fires on every engage, and re-entering a state you are already in would otherwise undo a set you picked by hand. A slot draws at most seven characters of its action's name, with a `.` on the end where it was cut - the stored record keeps the whole name, which is what `//hud crossbar list` prints and what the game is sent, and the edit-mode source mark is added after the cut so a slot reads the same either way. The active set is written between the two crosses in parambar's size and gold, with a sword above it while the weapon state is DRAWN (the component's own state, so it lights on `draw` even with nothing targeted) - so a set switch is visible on a bar with nothing bound to it, which is how its absence was found in a live client. Each is its own ANCHOR (`set`, `weapon`), so either moves without the bar; they are seeded where they used to draw, centred on the bar's centre column - which has no slot in it, unlike the middle row's two clusters, so anything drawn level with those lands on the art, exactly what the first attempt did. The label's foot is aligned with the BOTTOM slot row's foot; the sword's foot sits 8px clear of the MIDDLE row's top edge (the row slots 2 and 8 are in), lifted well clear of the label rather than stacked 2px above it now that nothing makes the two move together - and drawn at 36 rather than the 24 that fitted inside the label's own 40px band. The clearance is measured from the ROW, not written as a screen coordinate: the defaults are computed per resolution, so a fixed pixel would be right at exactly one. **The resting inventory is 365 prims - 244 images and 121 texts - constructed in the factory, at `core.register` time and so before login, and merely hidden** (a set switch repaints existing prims rather than allocating more), which is a resting cost only a live client can price; destroy-when-off is the fallback and is confined to the widget's build/refresh. Edit mode sits on top of that and is never resident: the binder builds its own window and rows when it opens and destroys them when it closes. It is **one** window - 920x600 at 18pt, dead centre, opened by clicking a slot and walking three steps (layer, then action, then target for the types that take one), with a `[ < back ]` in the top left that walks them in reverse and is absent on the first step, an `[ X ]` in the top right that closes from any step, and a details column where the floating tooltip used to be. The two were one control until 2026-08-31, a top-left button relabelled `[ close ]` on the step it could not retreat from. Three surfaces beside one another was the first design and failed in a live client: the stack panel opened beside its slot and drew UNDER the neighbouring slots' labels, and Windower renders every `texts` object above every `images` one, so no creation order could lift a backdrop clear of them. Item icons come from the shared `lib/icon_cache`; the ~1,300 shipped icons are load-checked by sampling, the party list's convention. Defects of the reference deliberately not reproduced: it `unbind`s `^f1`-`^f12` at load and never restores them (this takes no keybind at all), its bind is a non-atomic remove-then-insert that can lose the original, its no-target actions emit an unterminated quote, and its catalog gates a spell on `levels[job] <= job_level` - which **a merit spell can never satisfy**, since it encodes its requirement as a sentinel far above the cap (Refresh III at 1200), the defect that drove this port off the reference fork. Ours includes a known action whose requirement is above the cap when the job in question is the **main** one, because merits and job points apply to the main job alone (the same rule the stratagem gift follows). `skillchain.lua` transcribes the property and chain-resolution tables from the `SkillChains` addon (BSD, (c) 2017 Ivaar) and is fed parsed `0x028` packets by the widget rather than listening itself; the imported icon pack and UI art carry their notices in `assets/icons/`, `assets/cooldown/` and `assets/own/`, while the component's own `LICENSE.txt` covers the source transcribed into its Lua.

## Packaging & releases

[.github/workflows/package.yml](.github/workflows/package.yml) builds the distributable zip. It runs on pushes to `main` and `rc/**`, and on `v*` tags.

- **What it produces.** Everything in `src/` is copied into a single top-level folder **named after the repository**, then zipped (`XIVHud/…`). A user unzips it into `Windower4/addons/`, yielding `addons/XIVHud/`. The runtime `data/` dir is stripped from the package.
- **Folder/main-file rule.** Because the folder is the repo name, the main file must be `src/XIVHud.lua`, or Windower won't load it. The "Check source" step emits a `::warning::` when that file is missing — treat that warning as a real defect, not noise.
- **Delivery.** Branch pushes (`main`, `rc/**`) upload the zip as a **workflow artifact** (ephemeral). Pushing a `vX.Y.Z` tag additionally creates a **GitHub Release** with the zip attached (a semver pre-release tag like `v1.2.0-rc.1` is marked pre-release). Releases need `contents: write`, already granted in the workflow.
- **Build outputs** (`dist/`, `*.zip`) are gitignored.

## Line endings (important)

`.gitattributes` enforces **CRLF in the working tree** (`* text=auto eol=crlf`) because this targets Windows/Windower; git still stores LF-normalized blobs, so diffs stay clean. The sole exception is `.devcontainer/Dockerfile`, which is forced to LF for the Linux container. Don't fight the CRLF checkout — it's intentional.
